# Redis failover contract proposal

2026-11-11 · R0 design for Sentinel and Cluster. The next implementation step is discovery and validation of a candidate primary. Automatic resumption after promotion requires the authority and durability decisions below.

## Failure model

Cover primary or replica process crash, host loss, asymmetric partitions, replica lag, AOF rewrite or restart, delayed or lost replies, and Cluster slot movement. A partition can leave clients connected to a writable former primary. Sentinel and Cluster can promote a replica that lacks earlier acknowledged writes because they use asynchronous replication. [Redis Sentinel](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/), [Redis Cluster specification](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/).

Runwick's existing `redis-aof-always-single-primary-v1` profile covers local AOF acknowledgement on a directly addressed standalone primary. The current reconnect check compares store identity and the highest application revision observed by that process. Two divergent histories can pass that comparison. Preserve the standalone profile and name any promotion profile separately. [Redis store spec](../spec/22-redis.md#24-history-continuity), [client discovery and history code](../../src/Runwick.Redis/Store/RxClient.cs), [profile verification](../../src/Runwick.Redis/Store/RxProfile.cs).

## Acknowledgement and authority

A successful HA reply requires script publication, local AOF acknowledgement, and whatever additional acknowledgement the configured profile requires. `WAIT N T` counts replicas that received preceding writes on that client connection. `WAITAOF 1 N T` counts local and replica AOF fsync acknowledgements. Check the counts on every reply. A short count or disconnect after publication leaves the operation's outcome uncertain. Preserve the original command ID and body. [WAIT](https://redis.io/docs/latest/commands/wait/), [WAITAOF](https://redis.io/docs/latest/commands/waitaof/).

Both commands require the write and its acknowledgement to reach the same physical connection and node in order. Inside Lua or `MULTI`, they return the current count immediately. Runwick uses StackExchange.Redis 3.4.20, which shares physical connections across logical callers. Before relying on either command, qualify a supported transport that binds each write or bounded write group to its acknowledgement across reconnect, timeout and redirect. A trace must correlate the physical connection, primary, command IDs and returned counts. [StackExchange.Redis package pin](../../Directory.Packages.props), [multiplexer basics](https://stackexchange.github.io/StackExchange.Redis/Basics.html), [blocking operation discussion](https://github.com/StackExchange/StackExchange.Redis/issues/1961), [WAIT](https://redis.io/docs/latest/commands/wait/), [WAITAOF](https://redis.io/docs/latest/commands/waitaof/).

Require independent evidence for promotion eligibility and for exclusion of the former primary. A replica count describes acknowledgements at reply time. Sentinel and Cluster can later select another eligible replica. A strict profile needs a fixed, verified promotion set or an external authority that certifies continuity, plus a fence enforced at the write boundary or network/process fencing. An epoch stored only on a partitioned Redis primary can diverge along with the data. [Redis replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/), [Redis Sentinel](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/), [Redis Cluster specification](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/).

## Candidate admission policy

- **Verified primary.** Resolve the application or slot to its primary. Verify the node role, store identity, profile and revision. Resume only when the selected policy establishes continuity and the required fence.
- **Transition.** On loss of authority evidence, stop admitting new writes and claims. Invalidate local leases for the affected authority and apply the worker's cancellation and fencing rules. Keep unresolved commands available for resolution.
- **Continuity unresolved.** Report an unavailable store and retain original command identities. A missing receipt on a newly promoted history is ambiguous. Replay only after continuity is established or an operator reconciles the histories and certifies authority.

The first Sentinel fixture can implement discovery, reconnect, and fail-closed health before enabling resumption after promotion. Test Sentinel and data-node credentials and TLS separately, and keep ownership-sensitive reads on the selected primary. For Cluster, prove database-zero routing, slot-local script keys, `MOVED`/`ASK`, script reloads, and migration and management across primaries. An existing application hash tag places that application's state on one primary. Scale across independent applications first. Partitioning one application requires its own design for receipts, scopes, uniqueness, schedules and outbox. [Sentinel client guidance](https://redis.io/docs/latest/develop/reference/sentinel-clients/), [Redis Cluster specification](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/), [Redis store spec](../spec/22-redis.md#31-keys).

## Owner decision

The proposed first delivery discovers a replacement primary and keeps admission closed until continuity and authority can be verified. If the product requires automatic resumption, choose the supported failure envelope, the eligible promotion set and the fencing mechanism. An alternative profile with automatic promotion and possible acknowledged-write loss requires explicit approval. For any replica-acknowledged profile, choose `WAIT` or `WAITAOF`, replica count, timeout, AOF requirements and how the system handles an unresolved outcome. [Redis replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/), [WAITAOF](https://redis.io/docs/latest/commands/waitaof/).

## Qualification

Run one primary, two replicas and three Sentinels. Run three Cluster primaries with replicas and application keys on separate primaries. Inject failures before intent, during projection, after publication, during acknowledgement and before reply. Repeat during claim, renewal, finish, AOF rewrite, slot movement and failback. Test an old-primary partition that preserves worker access. Record each command's returned status, per-node receipts and jobs, permit and lease state, handler starts, duplicate executions, acknowledged loss, and time to verified recovery. A successful resumption must satisfy the selected profile and preserve the receipt and fencing checks under every supported fault.
