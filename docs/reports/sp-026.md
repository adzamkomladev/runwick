# SP-026 report: upgrades, rollback, drain and maintenance, restore

Date: 2026-11-08. Branch `worktree-agent-ad6ab0a90a91381cf`. Spec: [23-upgrades.md](../spec/23-upgrades.md). Runbooks: [upgrade](../runbooks/upgrade.md), [restore](../runbooks/restore.md), with the [transcript](../runbooks/transcript-2026-11-08.txt) of the commands that were run.

## What was built

In plain words: Runwick already had a migrator, gates and an admission mode stored per application, but the only way to change the mode was SQL typed by a test. Nothing told an operator what was safe, and nothing could give a copied database its own identity. This task adds the missing operator tools, writes down the rules, and proves each rule with a test.

1. **The rules** ([spec 23](../spec/23-upgrades.md)): a binary works with exactly one store revision, so an upgrade is "drain, stop old, migrate, reopen, start new", not a rolling upgrade. The rollback floor is the revision of the last migration: after it, the previous binary cannot run, and the way back is a restore, which loses history (a table of what is lost is in spec §7.3 and the restore runbook). Per-driver matrix of which UPG cases apply (§2).
2. **Operator calls on all three drivers** (`SetAdmissionModeAsync`, `GetStatusAsync`, `ReassignStoreIdAsync` on `RunwickPostgresMigrations`, `RunwickSqliteMigrations`, `RunwickRedisMigrations`), and CLI commands `store status`, `store admission` and `store reidentify` for PostgreSQL and SQLite. Drain and maintenance use the same statements as the old test-only gate change, with a 5 s wait that fails without changing anything. Maintenance is only reachable through drain. An identity change is refused unless every application is in maintenance and no live lease or worker presence is recorded.
3. **Two small fixes found while doing this:** a migrator whose database session is killed now reports `migration_connection_lost` (retryable, exit 4) instead of the CLI's generic "Unexpected ObjectDisposedException"; `ResolveCommand` now throws `StoreIncompatibleException` for a receipt whose codec or operation version it does not know instead of answering "conflict" or "not found". The CLI's agent envelope also no longer crashes on a command whose result is a list.
4. **Runbooks** with every step tied to a command that was run (transcript) or a test.

## What the runbook run showed (not predicted beforehand)

- A drained application refuses a **new process's startup handshake** (registering its queues is a creation path). The sample host crashed with an unhandled exception at startup while drained. So the order is migrate, **reopen**, start; spec 23 §4 and the upgrade runbook say so. The crash itself (an unhandled exception from `Host.StartAsync` in the sample, not from the library) is not fixed.
- A dump taken while processes were running contains unexpired worker presence rows, so `store reidentify` on a fresh restore refuses ("1 live worker presences") until they expire. This is the intended conservative behavior and the runbook explains it.
- Killing the migrator mid-run gave a generic internal error in the CLI before fix 3 above.

## Deviations and decisions (all marked [choice] in spec 23)

- One revision per binary and `expandCompatibleBinaries` empty are stated as the v1 rule; the older design papers' "additive expansion with compatible old binaries" is not a v1 promise.
- `open` to `maintenance` directly is refused (`drain_first`).
- Admission and identity changes run as the migration role and write `actor_subject` only, **no `management_audit` row**.
- No CLI for Redis: `Runwick.Cli` does not reference `Runwick.Redis` (package graph). Library calls exist and are tested.
- Spec 03 §10.2's "unless the migration manifest lists them" for maintenance is made concrete: no manifest lists any.
- "Old binary" in the tests means the same binary meeting a store whose revision was moved by one, or a mode set to `expand` (as for the RATE tests; no separately built older release is used). The upgrade steps themselves (interrupt, resume, 11 to 17) were run with the real CLI on a real database.

## Gaps (not done, said plainly)

- **Unknown receipt codec is named only on `ResolveCommand` for PostgreSQL.** The replay path inside the SQL functions (0009 to 0017) reports a foreign operation version as `command_conflict` (still fail-closed, nothing reapplied); SQLite and Redis do not read the codec version. Fixing the SQL path needs a new migration that replaces `rw_receipt_v1` for every operation; no second codec exists, so nothing can reach it in v1. Owed to the first migration that introduces one.
- No migration has a backfill or a concurrent index build, so the checkpoint column and the concurrent-index ledger phase are specified but untested (UPG-05 covers the failed-validate and kill-after-phase forms that exist).
- Real older-release binaries were not built; mixed-version behavior is simulated by moving the store's revision or mode.
- No audit row for admission and identity changes (above).
- Retention cleanup concurrent with a migration was not run: the revision gate refuses cleanup while the revision moves, which is stated in spec §10 rather than shown by a load test.
- Redis `GetStatusAsync` reports no lease or presence counts.
- (Fixed 2026-11-09) The sample host now catches the startup refusal when started against a drained application: it prints the message and exits 75 (retryable), as the upgrade runbook says.
- The final decision on whether this satisfies G-5 ("upgrade matrix per driver; runbooks executable") stays with the reviewer.
