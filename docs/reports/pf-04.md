# PF-04: batched operation bodies

Date: 2026-11-01. Host: the shared KVM guest (8 vCPU), **non-reference**. Store: `runwick-pg` (PostgreSQL 18) at 127.0.0.1:55499, through `docker-proxy`. Spec: 04 and 07 "Changes (2026-11-01, PF-04)".

## 1. What changed

Each operation was changed in its own commit, M2 operations first: Finish (with the shared close statements), Begin, Renew, Reserve, then Dispatch.

- **Locks first:** locks are taken in 04 §5 order. Reads that need only the request or the already-locked row are batched behind the locking statement.
- **Decision clock:** the clock read is appended as a separate statement to the batch that takes the last blocking lock. It is never placed in a locking statement's target list.
- **Generation read:** G stays a separate statement behind J, never a join. Under READ COMMITTED a joined, unlocked row would be re-checked from the snapshot taken before the lock wait.
- **Rate requirements:** Begin's `job_rate_requirements` check is an `EXISTS` in G's target list.
- **Effects and R4:** they go out as one batch.
  - Values that `RETURNING` used to supply are predicted from the locked rows and compared after the batch: the new revision, the execution number, and each fence (scope counter + 1).
  - Every row count is checked before COMMIT, and a mismatch rolls back with the same reply as before.
- **Kept on their own round trips:**
  - Dispatch items that provision scopes or rates;
  - the rate deferral path;
  - Reserve's live-permit count.
- **Fault points:** `AfterMutation` and `AfterLocksBeforeFreshTime` now fire once per batch (07 table). PGX-05, BATCH-01, ADM-03, TX-* and RUN-01 pass against the new boundary.

## 3. Floor, interleaved (PF-02 build, PF-04 build, PF-03 build; two rounds)

`floor --n 100 --warmup 10` on `rw_pf_a005`. The order was pf02-1, pf04-1, pf03-1, pf02-2, pf04-2, pf03-2. The load average was 4.4–7.8 throughout, lower than for the PF-01 and PF-02 runs. Times are p50 in ms.

| Run (load start → end) | Dispatch | Reserve | Begin | Renew | Finish | `SELECT 1` |
|---|---|---|---|---|---|---|
| PF-02 #1 (6.1 → 5.6) | 74.5 | 71.3 | 65.9 | 30.5 | 61.1 | 2.63 |
| PF-04 #1 (5.6 → 4.4) | 30.9 | 39.0 | 27.6 | 19.0 | 29.6 | 2.87 |
| PF-02 #2 (7.2 → 6.7) | 53.0 | 60.6 | 53.4 | 29.5 | 51.2 | 2.49 |
| PF-04 #2 (6.7 → 5.7) | 39.9 | 40.3 | 34.3 | 23.7 | 34.1 | 2.71 |

- **Change:** PF-04 is 25 to 58 % faster at p50 on every operation. Reserve went from 61–71 ms to 39–40 ms.
- **Reserve target missed on this host:** the PF-04 acceptance target (isolated Reserve p50 ≤ 25 ms) is not met here. A round trip through `docker-proxy` at this load costs about 5–7 ms, and Reserve's 6 round trips are about 26 ms of SQL wall time. The target was set for an isolated host without the proxy, and is to be checked on the reference environment (PQ1).

## 4. Not done in PF-04

- **Rated Begin is at 7 round trips, one over the target of 6.** The rate-scope lock keeps its own batch (UUID order after the concurrency scopes). The window counts follow it in a separate batch. Folding the window counts into the lock batch would meet the target; it is not done.
- **Scheduler and outbox operations are not batched.** Materialize, claim and ReceiveOutbox/settle only got the shared Dispatch-core change. Control edits, rate policy and PublishPresence are unchanged.
- **Reserve's live-permit count** (scoped jobs) and **Dispatch with scopes or rates** keep their sequential paths.
