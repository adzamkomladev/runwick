## Spec changes (dated 2026-10-31)

Recorded in 08 "Changes": RerunSucceeded stays in SP-011; the event cursor is in SP-011; the SQLite completion twin moves to SP-019; controls get their own `IJobControlStore` instead of methods on `IJobStateStore`. Implementation choices: the `durable` retention class for administrative receipts, the `(tx_id, event_id)` cursor bounded by `xmin`, client-side bulk controls, schema revision 2 with no mixed M2/M3 fleet, and a host-supplied trusted actor (authorization is SP-020). 03, 04, 05 and 06 carry matching Changes entries. 08 §3.1 rule 5 (schedule-row lock rank) was added by SP-016.

## Fixes found while testing

- TXC-02 (test only): the counters were read before the engine had observed the committed stage. The test now waits for the `completionCommitted` event first.
- TXC-03 (test only): the test awaited `ArmCommitReplyDrop`, whose task completes only after the drop, before sending COMMIT. That deadlocked the test. The arm is now started and awaited after the commit.
- MODE-05 (test only; failed in the full-suite run): the test required `FinishesSent = 0` and one observed stage per job, checked as soon as every job read `succeeded`. Two things broke that. The caller's commit makes the job `succeeded` before the engine settles the attempt. And under load the staged-receipt lookup (3 tries, each within `ControlRequestTimeout`) can stay unresolved, in which case 08 §8.2 sends the normal-path Finish; storage rejects it, because the staged Finish already closed the attempt. The test now waits until every attempt is settled by one of the two paths, and still checks one ledger row per job and none for cancelled jobs. TXC-02 keeps the strict single-job check.
- `EventsSince` and the control readers: typed `ExecuteAsync<EventPage>` instead of an object box; `IsDBNullAsync` instead of `IsDBNull` (CA1849).

## Limits and owed

- The MGMT-04 HTTP half, authorization and the dashboard are SP-020. Payload pruning in PGX-06 is harness pruning until SP-021.
- The SQLite twin of transactional completion is SP-019.
- MODE-01 … MODE-05 run in-process: several providers in one test process, not peer processes. The peer-process rerun is owed with SP-012 (15 §5).
- If the staged-receipt lookup stays unresolved, the engine sends a normal-path Finish (PermanentFailure, `staged_completion_not_committed`), which storage rejects for a committed stage. The outcome is correct, but the engine's diagnostic then reads like a failure. A longer or unbounded resolution for staged receipts is a possible refinement.
- The `ReferenceModel` invariant check runs on the committed snapshot after each mutation case. It is not a full history check of concurrent runs.
