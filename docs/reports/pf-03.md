# PF-03: prepared statements and warm control connections

Date: 2026-11-01. Host: the shared KVM guest (8 vCPU), **non-reference**. Store: `runwick-pg` (PostgreSQL 18) at 127.0.0.1:55499, through `docker-proxy`. Spec: 04 §9.2 and 04 / 07 "Changes (2026-11-01, PF-03)".

PF-03 was implemented after PF-04, on top of it, so its A/B baseline is the PF-04 build.

## 1. What changed

- **Statement preparation:** `Max Auto Prepare = 64` (`AutoPrepareMinUsages = 2`) on the control and work data sources. The migration connection stays at 0.
- **Plan stability:** every driver-owned connection starts with `-c plan_cache_mode=force_custom_plan`. Preparation saves parse and analysis, but each bind is still planned for its values, so the Reserve candidate query and the readiness probe plan exactly as before.
  - This is the plan's fallback, taken instead of an `EXPLAIN (GENERIC_PLAN)` case.
  - A startup option covers the bare-connection probe, which never enters the transaction frame.
- **`0A000` stale plan:** the runner handles it in this order:
  1. roll back;
  2. `UnprepareAll` on that connection;
  3. `Clear` the data source;
  4. retry the same command as a transient conflict.

  Read-only calls retry once. `MigrateAsync` clears the pools of every live store in its process on the migrated database.
- **Warm control pool:** control `MinPoolSize = 2`; the work pool stays at 0.
- **Unchanged:**
  - the staged paths, which keep the caller's settings;
  - PERF-01 counts.

## 2. Tests

All three new cases are in `PreparedStatementTests`.

- **PGX-11:** control and work connections run with `force_custom_plan`, and the control connection holds prepared statements.
- **DEP-08:** a column type that the gate statements return is changed while three loops run Dispatch, Reserve, Begin, Renew and Finish.
  - No call fails.
  - At least one `0A000` is retried (`PgRunner.StalePlans`).
  - The load keeps progressing, and there are no history violations.
- **PGX-12:** with `Connection Idle Lifetime = 2 s`, the control pool keeps min(opened, 2) of the same backends after 8 s idle, and the next Renew opens none.

## 3. Floor, interleaved (PF-04 build, PF-03 build; two rounds)

These are the same interleaved runs as in pf-04.md, in the order pf02, pf04, pf03 per round. The load average was 4.4–7.8. Times are p50 in ms.

| Run (load start → end) | Dispatch | Reserve | Begin | Renew | Finish |
|---|---|---|---|---|---|
| PF-04 #1 (5.6 → 4.4) | 30.9 | 39.0 | 27.6 | 19.0 | 29.6 |
| PF-03 #1 (4.4 → 7.2) | 27.5 | 33.6 | 25.4 | 20.6 | 25.8 |
| PF-04 #2 (6.7 → 5.7) | 39.9 | 40.3 | 34.3 | 23.7 | 34.1 |
| PF-03 #2 (5.7 → 7.8) | 32.7 | 37.2 | 27.5 | 25.6 | 30.7 |

- **Latency:** Dispatch, Reserve, Begin and Finish are 8 to 20 % faster at p50 in both rounds, even though each PF-03 run started at a higher load. Renew is within noise.
- **Comparison with the plan:** the gain is smaller than the plan's −34 to −40 % per call, because on this host network wait (5–7 ms a round trip through `docker-proxy`) dominates parse time.
- **Not measured:** client CPU was not measured (no `eng/run-perf.sh`).
