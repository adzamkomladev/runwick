# SP-027 report: integrated scenarios and samples

Date: 2026-11-08. Catalogue: [scenarios.md](../scenarios.md). Code: [samples/Runwick.Scenarios](../../samples/Runwick.Scenarios), runner [samples/run-scenarios.sh](../../samples/run-scenarios.sh).

## What was built

1. A plain-language catalogue of 33 scenarios (SCN-01 to SCN-33): the five deployment modes on each of PostgreSQL, SQLite and Redis (15), the management API and dashboard sign-in rules (3), schedules (3), capacity (3), drain and reopen (3), store outage (3) and the outbox (3).
2. One sample program, `Runwick.Scenarios`, with three commands: `list`, `run SCN-nn` and `node ...` (one deployment process; the scenarios start several of these as real operating-system processes). It is in the solution, builds with 0 warnings and passes `eng/check-package-graph.sh`. The runner script builds it, runs each scenario and prints one PASS or FAIL line.
3. The known gap from the SP-026 report is fixed: a process started while its application is drained now fails with a clear, retryable `AdmissionClosedException` ("Startup refused: the application's admission is closed (application_draining). Reopen it with 'runwick store admission --mode open', then start this process again."), not "Store handshake failed" as an incompatible store. The runtime does not remember the failure, so reopening and starting again works. The sample host turns it into exit code 75 and a one-line message; it no longer crashes. The upgrade runbook (step 5) and spec 23 §4 now say the supported order is migrate, reopen, start.

## Deviations from the brief

- **Outage on SQLite** is not a network outage: another connection holds the write lock for about 6 seconds. PostgreSQL and Redis outages are a small TCP relay inside the sample that cuts and refuses connections (the existing `PgFaultProxy` lives in a test project, so I did not reference it).
- **Redis outage** showed `DispatchOutcomeUnknownException` for the dispatch made during the outage (the connection dropped with a command in flight, so the outcome is genuinely unknown); PostgreSQL and SQLite showed `StoreUnavailableException`. The scenario accepts any Runwick error for the dispatch during the outage and requires recovery afterwards. It does not check whether the unknown dispatch was applied.
- **Auth** is checked on PostgreSQL only (it does not depend on the store). The "bearer" scheme is a small token handler in the sample, standing in for the host's real JWT or similar; Runwick only needs a non-cookie, non-Basic scheme.
- **Autoscaler** pass rule is "grew beyond 1, never beyond 6". It peaked at 2 in every run: the scenario proves it scales, not how far.
- **Admission** is driven through the library calls, not through the CLI command `runwick store admission` (same code; the CLI has its own tests).
- The brief asked for scratch databases "per scenario" on PostgreSQL: done (create and drop). Redis uses one of 15 numbered databases per scenario instead of a container per scenario.

## Gaps found

1. **No public way to activate the `scheduler` capability.** A schedule cannot be registered until the application raises capability `scheduler` (spec 13 §6.1), and the only caller is the internal `ActivateCapabilitiesAsync` store call used by the tests. A user who follows the guide gets `scheduler_not_active` at startup. The schedule scenarios (SCN-19 to SCN-21) work around it with that internal call, which needed one shared-file edit (see below). This needs a public API or a CLI/migrate step before release; it is not fixed here.
2. The CLI has no Redis support (known from SP-026), so Redis drain is only reachable from code.
3. The scenarios run on one machine. Nothing here proves a PostgreSQL or Redis on another host, TLS, or authentication on the store connection.
4. The dashboard scenario checks who is let in, not what the pages show (SP-024's browser runs).
5. The drain scenario does not hold a long-running job during the drain, so "running work renews and finishes while drained" is covered by UPG-04/PGX-01 only, not by a scenario.
