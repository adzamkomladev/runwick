# SP-021 Retention (PostgreSQL) — build report

Date: 2026-11-08. Spec: [17-retention.md](../spec/17-retention.md). Scope: PostgreSQL only. SQLite and Redis cleanup belong to SP-019 and SP-025.

## What was built

**Old records are now cleaned up automatically.** Each worker runs a background cleanup loop. It deletes data in small batches (at most 100 rows and 1 MiB of payload or error text per batch) and pauses between batches. It starts no new batch while the worker is under pressure or draining.

**What gets removed, and when (the defaults):**

- Payloads and error text of finished jobs: after 7 days (succeeded or cancelled) or 30 days (failed). The job itself stays visible, and its error codes stay.
- The whole job: after 90 days, and only once its detail has gone. A job is never removed while it still holds a uniqueness binding or a concurrency permit.
- Queue events follow job history. Audit rows go after 90 days, scaling events after 7 days, schedule occurrences after 30 days, and dead worker records after 24 hours.
- Records that protect correctness are deleted only when their own expiry passes, never because of the policy: command receipts, uniqueness keys, rate-limit grants and outbox mappings.

**Several processes can run cleanup safely.** Each record class has a progress row. A batch locks that row with SKIP LOCKED, so at most one batch per class runs at a time and the other processes skip it. A batch also uses SKIP LOCKED for every row it deletes, so it never waits on live work.

**A daily summary.** When a UTC day ends, each class writes one `RetentionSummary` audit row with that day's rows, batches and failures.

**Admins can change the policy.** Two new management routes:

- `GET {prefix}/v1/retention` (needs `Settings.Read`) shows the policy, its revision and each class's progress, including a "behind" flag when a class has not caught up in 24 hours.
- `POST {prefix}/v1/retention/policy` (needs `Retention.Manage`) changes the policy. It uses revision checks and writes one audit row with the before and after values.

`GetJob` now returns `detailExpiredAt`. `GetSettings` now returns `retentionPolicyRevision`.

**Schema revision 16** (`0016_retention.sql`) adds:

- the policy table and the progress table;
- the indexes cleanup needs;
- the two new audit kinds;
- new copies of the dispatch functions (`_v3`).

**A race fixed along the way.** Cleanup can delete a uniqueness key row in the moment between Dispatch creating it and locking it. That would leave a new job without its binding. Dispatch now repeats that step (at most 3 times, then reports `key_row_missing`). ManualRetry and RerunSucceeded seed the same key rows, so they got the same repeat.

**Options:** `AddWorker(w => w.Retention(o => ...))` sets `Enabled`, `BatchRows`, `BatchDetailBytes`, `BatchTarget`, `BatchPause` and `IdlePoll`. Values outside the allowed ranges are rejected at startup.

## Deviations from the spec

All are recorded in the spec's Changes list, dated 2026-11-08.

- `cleanup_progress` has an extra `pass_rows` column. Without it, the store cannot tell "a pass deleted nothing" from "the last batch deleted nothing".
- Classes where every scanned row is deleted keep no cursor; each batch simply restarts at the oldest row.
- Rate-grant and outbox-mapping cleanup skip a locked row instead of waiting up to 100 ms for it.
- The dispatch functions were copied to `_v3` and the `_v2` versions dropped, because released functions are never changed in place.
- A stale policy edit returns 409 `stale_revision`, as the other management edits do, not `revision_conflict`.
- The failure back-off (5 s doubling to 5 min) is fixed, not configurable.
- No `GRANT`s, because no runtime database role exists yet.
- Tests age records by moving their timestamps back with admin SQL instead of moving store time. OPS-05 runs at 5,000 jobs instead of 1,000,000.

## Gaps and risks

- **SP-032 merge:** `0016_retention` drops `rw_dispatch_core_v2`. SP-032's `management_dispatch_v1` (revision 17) must call `rw_dispatch_core_v3` instead, or its migration fails.
- **RET-01 (c)** (schedule occurrences racing Materialize and Trigger) has no test. The deletion code is the same simple age-ordered delete the other event classes use.
- **RET-01 (e)** races cleanup against Dispatch 20 times. It does not force the exact moment the key-row repeat needs, because that moment is inside a SQL function where no barrier can reach.
- **RET-01 (d)** checks only the expired side at 1 ms. The valid receipt keeps its natural 24-hour expiry, because moving it would change its stored deadline and break the replay.
- **OPS-04** does not seed outbox mappings or the source outbox, so those two parts are not checked there.
- **OPS-05** does not kill the process. It switches to a new store instance mid-pass, which also proves the cursor carries over. It does not measure a no-cleanup baseline or count lock waits.
- **CLN-03** triggers the failure with a lock timeout (a blocking table lock), not a statement timeout. It does not test the back-off timing.
- **CLN-04** covers drain only. The pressure-stop check is in the loop, but no test triggers it.
- **§6 source outbox relay cleanup** (deleting delivered rows in `Runwick.Outbox.Postgres` and `Runwick.Outbox.Sqlite`) is not built.
- **Every Postgres worker now runs the cleanup loop**, including in existing tests. It only touches records that are past their expiry, but a test that leaves expired receipts, keys or grants in place on purpose could now see them deleted. I ran WorkerTests and RateAdmissionTests to check this, and all 23 tests passed. The rest of the suite was not run.
- The completed-detail query filters on `state = ANY(...)`. On a very large backlog it may sort more rows than it needs to. This has not been measured at 1M rows.
