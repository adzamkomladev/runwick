## 5. Idle cost (no work; each role alone on its own database, 60 s after a 15 s settle)

| Role | Base statements/s | Final statements/s | Base CPU ms/s | Final CPU ms/s |
|---|---|---|---|---|
| worker | 8.0 | **2.36** | 118 | 138 |
| scheduler | 1.6 | **0.23** | 29 | 28 |
| relay | 1.76 | 1.80 | 46 | 75 |

- **Worker and scheduler:** before PF-08, 7 of every 8 idle worker statements were Npgsql's pool-reset sequence (`CLOSE ALL` … `UNLISTEN *`, 0.82/s each). `No Reset On Close` removes them (04 Changes 2026-11-02, PF-08; test POOL-01). What remains is the probe, presence and the listener's 30 s liveness ping (`SELECT $1`, 0.033/s).
- **Relay:** unchanged. The outbox source pool is not a Runwick store pool; it still sends `DISCARD ALL` per return. Applying the same setting there is a possible follow-up for spec 14.
- **CPU ms/s:** as noisy as the floor CPU (worker 118–189 ms/s across these runs). The idle backoff cap was deliberately left at 2 s (§6), so polling frequency is unchanged.

## 6. PF-07 notes

- **Wake latency:** not measured. On an idle worker, a notification removes the 100 ms … 2 s backoff wait, but that needs a latency workload on a quiet host.
- **Correctness:** OBS-01 now runs with the listener active and every notification dropped on receipt, and it asserts that notifications were received.
- **Commit cost:** a committing transaction that notified takes PostgreSQL's notify-queue lock briefly, so notifying commits serialize on it. Only dispatches with a job eligible now notify. P-01's 4.9/s cannot show this cost; it belongs in PF-09 on the reference host.
- **Deferred:** raising the idle backoff cap now that notifications ship. It would lower idle cost, but it changes OBS-01's bound and the 06 defaults, so it needs its own decision.
