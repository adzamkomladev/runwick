# SP-023 report: can the dashboard live inside someone else's app?

Date: 2026-11-08. Branch: `claude/competent-rubin-fcf93b` (not merged).

## The short answer

Yes, but not by using Inertia.Net 1.5.3 directly on the server side.

- **The browser side works as planned.** The React app with `@inertiajs/react` 3.9.1 renders, navigates, does partial reloads, posts commands and reloads cleanly after an upgrade, with a strict Content Security Policy and no server-side rendering. Assets are built ahead of time and embedded in the DLL, so a host app needs no Node.
- **The server side of Inertia.Net 1.5.3 cannot be scoped to one mount.** It keeps one set of options, one shared-props list, one asset version and one root page per application. Its middleware checks the version of *every* Inertia request in the app. A host that already uses Inertia.Net would therefore leak its shared props into our pages, or send our pages into a reload loop. Two dashboard mounts in one app cannot have different settings either. Version 1.6.3, the newest, has the same shape.
- **Decision: take the fallback the plan already named.** Runwick serves the small part of the Inertia protocol it uses from its own code, scoped to one mount (`DashboardMount`, about 400 lines). The React client, the page format and the management services stay the same. With it, DASH-01 to DASH-07 pass, apart from the WebKit browser run, which this machine cannot launch.

The other option, adding per-mount hooks to Inertia.Net and pinning a new release, stays open. You maintain that library, so this is your call. Runwick keeps the transport behind its own internal interface, so switching later does not touch the UI.

| Browser runs | `ClientApp/e2e/browser.sh` plus one `run-code` file per flow | Driven by `playwright-cli`: every check in Chromium, a smoke run in Firefox and WebKit |

How a mount works, in brief:

- `UseRunwickDashboardSpike` adds a **terminal branch** for its path. Nothing the host registers after it runs for dashboard requests. Endpoint routing is deliberately not used: in a `WebApplication`, routes mapped in a branch go into the app's global route table, where they could collide with host routes.
- Each request goes through these steps in order:
  1. authenticate and authorize with the mount's own policies;
  2. check the asset version;
  3. select props (for partial reloads);
  4. render.
- Each mount has its own:
  - antiforgery cookie, `rwk.{mountId}.csrf`, scoped to the mount's path;
  - token purpose (`Runwick.Dashboard.Csrf.v1` plus the mount ID);
  - asset build and asset version (a hash of every built file).
- The token goes in a `<meta>` tag in the HTML. It is never a page prop, so it never enters browser history.

## Evidence by case

Run on 2026-11-08 with the .NET 10.0.403 SDK:

- `dotnet test tests/Runwick.Dashboard.Spike.Tests`: 29 passed, 0 failed.
- Browser run (`e2e/browser.sh`, `playwright-cli` 0.1.22): 12 checks passed. WebKit did not launch (see DASH-07).
- `dotnet build Runwick.slnx`: no warnings or errors.

### DASH-01: two mounts in one app, and two apps in one process — passes

- Mounts `/ops-a` and `/ops-b` in one app, each with its own Basic scheme, user and data:
  - Alice, who exists only in A's scheme, gets 401 from B.
  - B's page does not contain A's data.
  - A's token and cookie, replayed by a B operator against B, get 403.
- Two apps in one process, both mounted at `/runwick`, each show only their own data. A token from one app is refused by the other, because each app has its own Data Protection keys.
- Adapter evidence: calling `AddInertia` twice configures the same unnamed options, and the last call wins. Through the adapter, two mounts cannot have different versions or shared props.

### DASH-02: an app that already uses Inertia — passes with the fallback; fails with the adapter

- Requests to the host's own route `/` (full HTML, Inertia JSON and a stale-version request) give byte-for-byte the same responses with and without the dashboard mounted.
- Dashboard pages contain none of these host settings:
  - its shared prop (`hostUser`);
  - its root page (`<title>host</title>`);
  - its version (`host-1`).
- A host fallback route (`MapFallback`, which catches every unmatched path) does not capture the mount.
- **Two failures, both recorded as tests:**
  1. A page rendered with Inertia.Net's own `Render` inside such a host carries the host's shared props and version. This is why the adapter itself was not used.
  2. If the host calls `app.UseInertia()` *before* mounting the dashboard, the host's middleware answers dashboard requests with its own version check. The response is 409 with `X-Inertia-Version: host-1`, and the client reloads forever. **Rule for hosts: mount the dashboard before `UseInertia()`.** The mount cannot detect the wrong order by itself.

### DASH-03: login, cross-site request protection, refused requests — passes

- **Basic auth:** a missing or wrong password gets 401 with a `Basic realm` challenge. A request that is both logged out and on an old version gets 401, not the version 409, so authentication runs first.
- **Host cookie login:** a logged-out full page load gets a 302 to `/login`. The same request from the Inertia client gets 409 with `X-Inertia-Location: /login`. Inertia's background request cannot follow a redirect to a login page, so the client is told to load that page in full.
- **OIDC (OpenID Connect):** stood in for by a cookie scheme whose challenge goes to an external identity provider (`https://idp.example/authorize`). The Inertia client gets 409 with that address. After the host signs the user in, the same permission checks apply. A view-only user is sent to the cookie scheme's access-denied page. A real OpenID Connect provider was not run.
- **Cross-site request protection (CSRF):** retry is refused with 403 when:
  - the token is missing;
  - the token is forged;
  - the token belongs to another user;
  - the user can only view.

  A GET to the retry address gets 405. A forged `X-Inertia` header grants nothing. Nothing ran in any of these cases (`Applied = 0`).
- **Refused reads:** a view-only user who asks for the operator-only `audit` prop in a partial reload gets 403. Asking to reveal a payload also gets 403. An operator gets the prop and the payload. The payload response is `no-store`.

### DASH-04: hostile text, history, CSP, caches — passes

- A job named `</script><script>alert(1)</script>"'&<img …>` plus U+2028:
  - the initial HTML contains no raw `<script>alert`, `<img` or U+2028 (the JSON is escaped);
  - the data comes back unchanged;
  - the title is HTML-encoded.
- In the browsers, the name shows as plain text. No dialog opens and no `<img>` element is created.
- **Content Security Policy:** `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`. The browsers reported no violations. This needed two client settings:
  - `progress: false`, because Inertia's progress bar injects an inline `<style>`;
  - `modulePreload.polyfill: false`, because the polyfill is an inline script.
- **Caching:** HTML, JSON, 401 and payload responses are `no-store, private` with `Vary: X-Inertia`. Assets are `public, max-age=31536000, immutable`, because their names contain a hash of their contents.
- **History:** pages set `encryptHistory`. In Chromium, `history.state.page` is an encrypted `ArrayBuffer`, and neither the job name nor a revealed payload appears in it. Page JSON never contains the payload or the token.

### DASH-05: path prefixes, proxies, redirects — passes

- Behind `UsePathBase("/ops")`, these all carry the `/ops/runwick` prefix:
  - asset addresses;
  - the page `url`;
  - the `base` prop;
  - the cookie `Path`;
  - the 303 after a retry.
- The `X-Forwarded-Prefix` header is applied only from a known proxy:
  - from `10.0.0.1`, the base becomes `/edge/runwick`;
  - from `203.0.113.9`, the header is ignored.
- Redirects are always built from the mount path plus an escaped ID. An ID of `\\evil.example` redirects to `/runwick/jobs/%5C%5Cevil.example`, never to another host.

### DASH-06: asset upgrades, ambiguous commands — passes

- **Old client, new server:** a visit sent with the old version gets 409, `X-Inertia-Location` set to the same address, and an empty body. The old hashed file now gets 404; the new one is served.
- **Browser upgrade test:** the sample host was stopped and restarted with a rebuilt client. The next click in an open tab triggered a full page load, and the page then used the new `…-v2.js` entry.
- **Retry sent by an old client:** it runs once and returns 303. The follow-up GET gets the version 409, and the full reload is a plain GET, so it never re-sends the POST. Sending the same command ID again does not run it a second time (`Applied = 1`).
- **Unknown result or revision conflict:** the answer is the job page itself, a 200 with `X-Inertia: true`, an `outcome` of `unknown` or `conflict`, and the original command ID. It is not a redirect, which would look like success. It is not a 409 either, which the client would take as the asset-version signal.

### DASH-07: standalone without workers, embedded without side effects — passes; WebKit not run

- **Standalone:** an app with only the dashboard and authentication serves it. No Runwick hosted service is registered.
- **Embedded:** `AddRunwickDashboardSpike()` adds only Data Protection, authorization and options services. It adds no startup filter, MVC filter, shared props or default authentication scheme. Two caveats:
  - In an app without Data Protection, its key-ring hosted service is added. That is ASP.NET's own service, and the only hosted service added.
  - `AddAuthorizationCore()` alone made `WebApplication` crash at startup: the app auto-adds `UseAuthorization`, which then finds incomplete services. The spike uses `AddAuthorization()`, so in hosts that had no authorization, the framework's (no-op) authorization middleware now runs.
- Startup refuses these mounts:
  - a missing view or operate policy (there is no implicit anonymous mode);
  - a bad path (`/`, upper-case, a trailing `/`);
  - a bad mount ID.
- **Browsers:**
  - Chromium ran all 11 checks.
  - Firefox ran the smoke check (load, navigate, retry, no CSP violations).
  - **WebKit was not run:** this machine lacks about 30 system libraries (gtk4, gstreamer, …), and installing them system-wide was out of scope. Run `e2e/browser.sh webkit` on a machine with the Playwright WebKit dependencies before SP-024 closes DASH-07.

## Limits and follow-ups for SP-024

- **Mount order** is a documented rule (mount before `UseInertia()`), not something the code checks. The same applies to any host middleware placed *before* the mount: it still runs for dashboard requests, as it does for static files.
- **Route collisions:** host routes under the mount path become unreachable and are not detected yet. SP-024 should check for them when the app starts.
- **The data interface** (`IDashboardSpikeData`) stands in for the SP-020 management services. The real dashboard calls those.
- **Basic auth:** the spike's handler is a test helper. SP-024 decides the shipped Basic setup (HTTPS requirement, password storage).
- **Unused protocol features:** deferred, merge and once props, error bags, flash data and history clearing on logout are not implemented, because the spike does not use them. Add them only when a page needs them.
- **Old assets during a rolling deploy:** a new server does not serve an old build's files. A client is safe because the next visit reloads in full. A tab that lazily loads a chunk *before* its next visit could still get a 404. The spike has no lazy chunks.
- **Browser run setup:** the browser run uses the `playwright-cli` installed on this machine (0.1.22). It opens one session per browser and user, passes the Basic credentials in a generated config, and runs each flow with `run-code`. `playwright-cli` is not pinned by the project; pin it when the run moves to CI.
