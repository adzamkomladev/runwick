# SP-023 report: can the dashboard live inside someone else's app?

Date: 2026-11-08. Branch: `claude/competent-rubin-fcf93b` (not merged). Updated the same day for Inertia.Net 1.7.0.

## The short answer

Yes. The dashboard runs on **Inertia.Net 1.7.0**, with each dashboard mount registered as one of its new *named mounts*. The React client and the page format are unchanged. DASH-01 to DASH-07 pass in the protocol tests, in Chromium and in the Firefox smoke check. WebKit was not run, because this machine lacks its system libraries.

- **What changed since the first run.** Version 1.5.3 kept one set of options, shared props, asset version, root page and state cookie per app. So the first version of the spike carried its own copy of the protocol. Version 1.7.0 adds `AddInertia(name, ...)` and `UseInertia(name)`. A named mount gets its own options, shared props, asset version, state cookies and root view (a keyed `IInertiaRootView`). The dashboard now uses that, and the Runwick-owned protocol code is gone. Removed from Runwick: page JSON, the asset-version 409, partial reloads, `Vary`, and 303 redirects.
- **What 1.7.0 still does not do per mount.** Six gaps remain, listed under "Gaps Runwick still covers" below. Runwick's code covers each one, in `DashboardMount`. Two of them matter most:
  - **Mount order:** a host that calls `app.UseInertia()` *before* mounting the dashboard still sends dashboard pages into a reload loop.
  - **JSON settings:** the host's JSON settings still reach a named mount's props.

## Gaps Runwick still covers (exactly)

| # | What 1.7.0 does not do | Effect if ignored | What Runwick does | Test |
|---|---|---|---|---|
| 1 | The host's default `UseInertia()` middleware does not skip requests belonging to another mount | If the host's middleware runs before the dashboard's branch, it checks dashboard requests against the host's asset version. Dashboard visits get 409 `X-Inertia-Version: host-1` and the client reloads forever. The middleware would also load and clear the host's flash state. | Rule for hosts: mount the dashboard **before** `UseInertia()`. It is documented on `UseRunwickDashboardSpike` and cannot be detected from inside the mount. | `Host_UseInertia_before_the_mount_answers_dashboard_visits_with_its_own_version` |
| 2 | Named mounts serialize props with the host's `HttpJsonOptions` (naming policy, converters) | If the host sets, say, `SnakeCaseUpper`, `job.name` reaches the client as `job.NAME` and the UI breaks. The HTML-safe encoding still holds. | Object props are passed as `JsonElement`s serialized with Runwick's own options; those are written as is. | `A_host_JSON_naming_policy_reaches_named_mounts_but_not_the_dashboards_props` |
| 3 | Inertia.Net's antiforgery uses the app-wide `IAntiforgery` and `AntiforgeryOptions` | One app-wide token and cookie, not per mount | Per-mount token: cookie `rwk.{id}.csrf`, scoped to the mount path; a Data Protection purpose per mount; bound to the user | `Mutations_need_this_mounts_token_for_this_principal_and_never_run_on_GET`, two-mount test |
| 4 | Only redirects to *other origins* become a full page load for Inertia requests | A same-origin login or access-denied page outside the mount is fetched by XHR, and the client shows an error modal | Any redirect that leaves the mount becomes 409 + `X-Inertia-Location` | `Host_cookie_and_OIDC_style_challenges_become_full_visits_for_Inertia_requests` |
| 5 | No per-prop authorization | A view-only user could ask for an operator-only prop in a partial reload | Runwick refuses such a partial reload with 403 before rendering | `Denied_partial_reloads_and_reveals_are_refused` |
| 6 | Assets come from a Vite manifest on disk | No embedded-resource serving | Runwick serves the embedded build itself, with immutable caching. It also sets `no-store`, `nosniff` and the CSP. The CSP is set in its keyed root view, which also writes the head. | DASH-04 tests |

Two behaviours are composition rather than gaps. They are listed so nobody re-adds them by mistake:
- Authorization runs in a gate placed before `UseInertia(name)` inside the branch, so login and permission checks come before the version check.
- `DashboardMount` is the mount's keyed `IInertiaRootView`.

Adapter behaviours the tests now expect:
- The asset-version 409 sends an **absolute** `X-Inertia-Location`.
- Every page carries an `errors` prop.
- The page JSON in the HTML escapes `/`.

## What was built

| Piece | Where | What it is |
|---|---|---|
| Spike library | `src/Runwick.Dashboard.Spike/` | Two entry points. `AddRunwickDashboardSpike(id, options)` registers the Inertia named mount `runwick-{id}` and its keyed root view. `UseRunwickDashboardSpike(path, id)` maps a terminal branch. Also: `DashboardMount` (about 390 lines: the gaps above, routing, the stand-in commands), embedded assets, a stand-in data interface and a test Basic-auth handler. Not packable. |
| React client | `src/Runwick.Dashboard.Spike/ClientApp/` | Two pages, built by Vite into `dist/` and committed. That folder is embedded as resources. |
| Protocol tests | `tests/Runwick.Dashboard.Spike.Tests/` | 30 tests over in-memory hosts, tagged `Item=SP-023` and `Case=DASH-0x` |
| Sample host | `samples/Runwick.Dashboard.SpikeHost/` | An app using Inertia.Net 1.7.0 for its own page at `/ops/`. The dashboard is mounted at `/ops/runwick`, before the host's `UseInertia()`. |
| Browser runs | `ClientApp/e2e/browser.sh` plus one `run-code` file per flow | Driven by `playwright-cli` 0.1.22: every check in Chromium, a smoke run in Firefox and WebKit |

Requests through a mount pass these layers in order:
1. Runwick's gate: assets, response headers, view authorization.
2. Inertia.Net's middleware for `runwick-{id}`: asset version, state cookies, redirects.
3. Runwick's pages, which render with `Inertia.Render(...)`.

The registration API changed to two steps, because named Inertia options must exist at service-registration time.

## Evidence by case

Run on 2026-11-08 with the .NET 10.0.403 SDK and Inertia.Net 1.7.0 restored from nuget.org:

- `dotnet test tests/Runwick.Dashboard.Spike.Tests`: 30 passed, 0 failed.
- `e2e/browser.sh chromium firefox`: 12 checks passed.
- `dotnet build Runwick.slnx`: no warnings or errors.

### DASH-01: two mounts in one app, two apps in one process — passes

- Mounts `ops-a` and `ops-b` in one app:
  - each has its own Basic scheme, user and data;
  - a user of A gets 401 from B;
  - B shows none of A's data;
  - A's token and cookie, replayed against B, get 403.
- Each mount is its own Inertia named mount:
  - its own asset version: two builds give two versions;
  - its own state cookie (`.Inertia.State.runwick-ops-a` and `…-ops-b`);
  - its own root view.
- The host's default mount keeps its version (`host-1`).
- Two apps in one process, both mounted at `/runwick`, keep their data and tokens separate.

### DASH-02: an app that already uses Inertia — passes, with the order rule

- Requests to the host's own route (full HTML, Inertia JSON and a stale-version request) give byte-for-byte the same responses with and without the dashboard mounted.
- Dashboard pages contain none of the host's shared prop, root page or version.
- A host fallback route does not capture the mount.
- A host JSON naming policy changes props in a plain named mount, but not dashboard props (gap 2).
- **Known failure, pinned by a test:** with the host's `UseInertia()` placed *before* the mount, dashboard visits get the host's 409 (gap 1).

### DASH-03: login, cross-site request protection, refused requests — passes

- **Basic auth:** a missing or wrong password gets 401 with a `Basic realm` challenge. A request that is both logged out and on an old version gets 401, not 409, so authentication runs before the adapter's version check.
- **Host cookie login:** a logged-out full page load gets a 302 to `/login`. The Inertia client instead gets 409 with `X-Inertia-Location: /login`.
- **OIDC (OpenID Connect):** stood in for by a cookie scheme whose challenge goes to an external identity provider. The Inertia client gets 409 with the provider's address. A view-only user is sent to the access-denied page. A real OpenID Connect provider was not run.
- **Cross-site request protection (CSRF):** retry is refused with 403 when:
  - the token is missing;
  - the token is forged;
  - the token belongs to another user;
  - the user can only view.

  A GET to the retry address gets 405. Nothing ran in any of these cases.
- **Refused reads:** a view-only user who asks for the operator-only `audit` prop in a partial reload gets 403. Asking to reveal a payload also gets 403. An operator gets only the requested prop (plus `errors`), and the payload with `no-store`.

### DASH-04: hostile text, history, CSP, caches — passes

- A job named `</script><script>alert(1)</script>"'&<img …>` plus U+2028 is escaped in the initial HTML by the adapter's HTML-safe page writer. The data comes back unchanged and the title is encoded. In the browsers, the name shows as plain text, with no dialog and no `<img>` element.
- **Content Security Policy:** `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`. The browsers reported no violations. The client keeps `progress: false` and `modulePreload.polyfill: false`, because both would otherwise inject inline code.
- **Caching:** pages, JSON, 401 and payload responses are `no-store, private` with `Vary: X-Inertia`. Assets are immutable.
- **History:** in Chromium, `history.state.page` is an encrypted `ArrayBuffer`, because the mount sets `EncryptHistory`. No payload or token appears in page JSON.

### DASH-05: path prefixes, proxies, redirects — passes

- Behind `UsePathBase("/ops")`, asset addresses, the page `url`, the `base` prop, the cookie path and the 303 after a retry all carry `/ops/runwick`.
- `X-Forwarded-Prefix` is applied only from a known proxy (`/edge/runwick`) and ignored from anywhere else.
- Redirects are built from the mount path plus an escaped ID (`\\evil.example` → `/runwick/jobs/%5C%5Cevil.example`).

### DASH-06: asset upgrades, ambiguous commands — passes

- **Old client, new server:** a visit sent with the old version gets 409 with the absolute `X-Inertia-Location` and an empty body. The old hashed file now gets 404; the new one is served.
- **Browser upgrade test:** in Chromium, the sample host was restarted with a rebuilt client. The next click in an open tab triggered a full page load, and the page then used the new `…-v2.js` entry.
- **Retry sent by an old client:** it runs once and returns 303. The follow-up GET gets 409, and the reload never re-sends the POST. Sending the same command ID again does not run it twice.
- **Unknown result or revision conflict:** the answer is the job page itself, a 200 with `X-Inertia: true`, an `outcome` and the original command ID. It is neither a redirect nor a 409.

### DASH-07: standalone without workers, embedded without side effects — passes; WebKit not run

- **Standalone:** an app with only the dashboard and authentication serves it, and no Runwick hosted service is registered.
- **Embedded:** registering the dashboard adds no startup filter and leaves the host's default Inertia options untouched. `AddInertia(name, ...)` does add some framework registrations even in a host that never used Inertia:
  - Inertia.Net's default-mount services;
  - its hosted services: a bounded refresh queue, used only by cached props, plus an SSR process manager and a TypeScript writer, both idle without configuration;
  - a memory cache, an HTTP client and metrics;
  - Data Protection's key-ring hosted service, if the host had none.

  The test checks that every hosted service comes from Inertia.Net, Data Protection or the web host itself.
- Startup refuses:
  - at registration: a bad mount ID and a missing policy (a duplicate mount ID is also refused, but no test covers it);
  - at mapping: a bad path and an unregistered mount.
- **Browsers:** Chromium ran all 11 checks and Firefox the smoke check. **WebKit was not run:** this machine lacks about 30 system libraries (gtk4, gstreamer, …). Run `e2e/browser.sh webkit` on a machine with the Playwright WebKit dependencies before SP-024 closes DASH-07.

## Limits and follow-ups for SP-024

- **Gaps 1–4 belong upstream.** They would be natural additions to Inertia.Net:
  - the default middleware skipping requests that another mount owns;
  - per-mount JSON options;
  - per-mount antiforgery;
  - an option to load any redirect that leaves the mount in full.

  Each one fixed there lets Runwick delete its matching code.
- **Route collisions:** host routes under the mount path become unreachable and are not detected yet. SP-024 should check for them when the app starts.
- **The data interface** (`IDashboardSpikeData`) stands in for the SP-020 management services.
- **Basic auth:** the spike's handler is a test helper. SP-024 decides the shipped Basic setup.
- **Old assets during a rolling deploy:** a new server does not serve an old build's files. A client is safe because the next visit reloads in full. A lazily loaded chunk could still get a 404; the spike has none.
- **Browser run setup:** the run uses the machine's `playwright-cli` (0.1.22), which the project does not pin, and the flow files assume port 5791.
