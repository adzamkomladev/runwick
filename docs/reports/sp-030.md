# SP-030 report: release packaging, licences, documentation, defaults

Date: 2026-11-08. Status: review-ready. G-6 is not passed yet; it waits on SP-028 and SP-029 and on the owner's decisions below. Nothing was published or pushed; there is no remote.

## What was built

- **Package metadata** for all 13 packable projects, set once in `Directory.Build.props`: id, description (already per project), MIT licence expression, README (`eng/PACKAGE-README.md`, packed as `README.md`), project/repository URL, tags, copyright, deterministic build, symbols as `.snupkg`. The repository URL is a placeholder (`example.invalid`) because no remote exists. SourceLink is left out for the same reason. `LICENSE` (MIT) added at the root.
- **`eng/check-release.sh`**: packs every `src` project into `artifacts/packages` (already gitignored) and fails on any pack warning. Then, for each package, checks: id, version, description, authors, licence `MIT`, README inside, project and repository URL, a symbols package, the dependency list against `eng/package-graph.json`, only `net10.0`, framework references, and no files other than the library, its XML docs, README, notices, the shipped Grafana/Prometheus files and (for the CLI) the tool payload. Result: 13 of 13 pass, 0 warnings.
  - One finding: central transitive pinning (`CentralPackageTransitivePinningEnabled`) makes NuGet list transitive packages (for example Cronos and NodaTime on `Runwick.AspNetCore`) as direct dependencies of each package. They are harmless and already pinned, so the check allows extra dependencies only if they are pinned in `Directory.Packages.props`; required ones must all be present. If you would rather have clean dependency lists, the pinning setting has to go, and that is a decision about security pinning, so I left it.
- **`eng/check-licenses.sh`** with allow-list `eng/license-allowlist.txt`, and **`docs/release/licenses.md`** (allow-list reasons, what was found, bundled SQLite). **`THIRD-PARTY-NOTICES.md`** holds the licence text of the 10 npm packages in the dashboard bundle and is packed into `Runwick.Dashboard` (the check enforces that).
- **Documentation** in `docs/guide/` (index plus getting started per store, delivery semantics, cancellation, topology, configuration, management/dashboard/CLI, observability), written against the spec's "Must not claim" sections.
- **Defaults test** `tests/Runwick.Core.Tests/DefaultsMatchCodeTests.cs` (trait `Item=SP-030`): reads the tables in `docs/spec/06-defaults.md`, `17-retention.md` §4.4, `20-sqlite.md` §10 and `22-redis.md` §10 and compares about 80 rows with the option classes and constants (worker, producer, outbox relay, scheduler, retention, SQLite, Redis, and the job defaults a registry gives an unconfigured job). I changed one doc value temporarily to confirm it fails. The list of defaults that cannot be checked mechanically is `NotCheckedMechanically` in the test file. To reach the outbox options the test project now references `Runwick.Outbox`.
- `docs/release/release-checklist.md`: the steps left for the owner.
