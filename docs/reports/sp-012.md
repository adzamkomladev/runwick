## Fixes found while testing

- **Known release did not lift the queue cooldown (engine; found by RDY-01 in the full-suite run).** A retiring attempt removed its queue from the probe exclusion, but the queue-scope cooldown from the CapacityBlocked reply stayed. Under load, the backlog then drained about two jobs per cooldown or idle period (≤ 2 s): roughly 500 s for 500 jobs, against the 3-minute assertion. Now `OnAttemptRetired` also wakes the pool, and a dequeued release clears that queue's cooldown (`LaneSelector.ReleaseQueue`). Lane cooldowns stay, as 09 §4.2 requires.
- **The draining presence row was never written (engine; found by MODE-P).** The draining publication ran under control stop, and `StopAsync` cancelled control stop before the write finished. `StopAsync` now waits for the publication, bounded by 2 s, before cancelling. A timeout is diagnosed, not thrown.
- RDY-02 (test only): the query read `closed_at`; the column is `finished_at`.
- `PgStore.Readiness`: `IsDBNullAsync` instead of `IsDBNull` (CA1849).

Owed-case work (2026-11-01): no product defect was found and no product code changed. Test and harness changes:

- RDY-01 queue-scope test (test only): its drain bound went from 3 to 8 minutes. On the shared host (load average 14–35 on 8 vCPU) the 500-job drain measured about 2.6 jobs/s with Reserves ≈ successes + 25 % (no stall, no cooldown pile-up): the rate is one serial Reserve round trip per admission, and 500 jobs needed about 190 s alone and up to 8 min beside the other classes.
- MODE-05 peer rerun (test only): reading the cursor from the start for each of four victims through the peer exceeded the 90 s channel timeout under load. The victims' `job_cancelled` events with the actor are now checked in the store, and one is observed through a worker process's cursor (3 min bound).
- MODE-02 peer rerun (test only): it first asserted one attempt row per job. In one run two jobs had a second attempt: a reservation that never began (abandoned or released before Begin on the loaded host) followed by the executed one, which the engine allows (05 §9.2, RUN-01 rules). The case's "each processed once" is now asserted as exactly one executed attempt per job, which succeeded, plus one handler invocation per job across the three processes.
- CAP-01 fixed-pool tests (test only): in one run the store showed 6 pending jobs where 8 were expected while invocations (20) and the sampled gate maxima (8, 8, 16) held. A reservation whose lease margin cannot be confirmed before Begin is given up without an invocation (05 §9.3, `lost:SafetyDeadline`) and the job stays `reserved` until expiry recovery; the same mechanism explains the MODE-02 extra attempts. The tests now count pending plus such reserved jobs (asserting each reserved job is matched by a given-up reservation event) and require exactly one executed, succeeded attempt per job.
- RDY-02 / WRK-19 test (test only): one run read `Unhealthy` instead of `Degraded` at the instant publication was seen failing; a slow renewal on the loaded host can briefly raise pressure (the worker ranks a suspended pool or pressure above failing publication). The test now waits for `Degraded` while publication keeps failing.
- Lane-share test (test only): the wait for 100 admissions went from 90 s to 5 min (one serial Reserve per admission at 0.3–1 s on the loaded host).
- Harness: `WorkerHost.Create(worker:)` adds pools to the group; the peer worker gained `queue`, `bcs` (staged completion), a `long` handler and the `workerStats`, `workerDispatch`, `workerPause`, `workerResume`, `workerCancel`, `workerObserve` commands (15 "Changes").

## Limits and owed

Owed before acceptance:

- the G1-M1 and G1-M3 reruns, P-04 and P-05 at 1/3/6 replicas (15 §11). These are measurements on the reference host with `eng/run-g2.sh`, which does not exist yet (`g2.md` §5); this shared host is not the reference host.

Deferred or not covered, with the reason:

- CAP-01 "target 0 suspends admission" and target reductions: a runtime target change exists only as `SetPoolOverride/1` on automatic pools (11 §5), so they remain the SP-014 sub-part (07 C-8, G1CaseTable deferred list).
- CAP-02 "a failed claim leaves scores unchanged" and CAP-03 threshold equality and lower-lane rotation are proved only by the Pure half (`CapacityCaseTests`): no real-store trigger makes a failed claim deterministic, and a store clock cannot be held at one millisecond without the faketime image (15 "Changes").
- PGX-07: a lane whose head is a long run of unsupported jobs makes the probe's supported-head lookup walk that run in `jobs_ready`; it was not measured. Whether to add a type-oriented index is the 09 §5 decision, left to measurement (performance work, SP-031). The diagnostic plan ran with no live worker, so its capability and subscription lookups did not execute; they are per tuple group, not per job.
- `RequiresDocker`: the SP-012 tests carry it only where container control is needed (07 §1.1), which is none of them; the trait is omitted (15 "Changes").
- The 10,000-job type-scope case does not drain its whole backlog (50 more successes show it moves): at about 2–3 jobs/s on this host a full drain would take about an hour.
