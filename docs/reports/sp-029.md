# SP-029: performance, contention, recovery and soak qualification

Date: 2026-11-09. Store: PostgreSQL 18 (the reference store). Plan: [performance acceptance plan](../architecture/performance-acceptance-plan.md).

## The short version

- Every P-case in the plan now has a workload, and one script runs them all: `eng/run-sp029.sh`. It writes a
  `summary.md` with one verdict per threshold.
- I ran the **short profile** of every case and a **10-minute soak** on the shared test machine. That machine is
  not the reference host: 8 shared CPUs, the database in a container on the same machine, and a load average of 2 to 18
  during the runs. **Every number below is informational. None of them passes or fails a threshold.**
- No correctness problem in any case: zero violated invariants, zero lease losses, zero duplicate deliveries.
- Two thresholds look out of reach with the current defaults, whatever the host: the P-06 scheduler lag and probably
  the P-09 relay rate. They are listed under "Proposed threshold revisions" for you to decide. I changed no threshold.
- One harness bug found and fixed: the workload runner hid the store's cleanup support from the worker. Cleanup never
  ran in any earlier G-1, G-2 or PF workload. It runs now.
- **Still needed for qualification:** the full profile and a 24-hour soak on a dedicated quiet host (commands below).

## What was added

| Piece | What it does |
|---|---|
| P-03 (new) | Payload pressure. 64 KiB jobs at 16/s and 1 MiB jobs at 1/s (about 1 MB/s in), with the P-01 handler. Checks that a payload one byte over 1 MiB is refused with `payload_too_large` and stores nothing. Records memory allocated per job in worker and producer, and database log (WAL) bytes per job. |
| P-07 (new) | Management under load. P-01 runs. Then 1,000,000 finished jobs are copied into the store from real finished jobs, spread over the last 30 days, so cleanup has work. Then a 15-minute baseline window, then a 15-minute window with 20 dashboard viewers each polling every 5 s (job list, succeeded filter, pending filter, queue list). Measures list latency, worker throughput lost to the viewers, and extra table-scan rows per poll (an exact count over the job table would show up here). |
| P-10 (new) | Soak. Runs `--duration-min` (24 h by default) at 70 % of the P-02 sustainable rate. 2 % of jobs fail once and retry, 0.2 % fail for good, 100 schedules fire every minute, and retention is short (job detail 1 h, history 2 h) so cleanup runs all the time. The worker reports its managed heap after a forced full garbage collection, and its live caches, every 5 minutes. |
| P-01t (new) | Instrumentation cost. The same P-01 with telemetry off, then with every Runwick trace and metric recorded by in-process listeners. |
| `eng/run-sp029.sh` | Runs the cases in order, each on its own database server. `SP029_PROFILE=short` (default) or `full`. `SP029_SOAK_MIN` sets the soak length. `SP029_REFERENCE=1` turns informational verdicts into PASS/FAIL. `SP029_PG` points the runs at a separate database host. |
| `eng/sp029-summary.py` | Reads the results and writes `summary.md`: threshold, measured value, rule, verdict. |
| Harness fix | `TimingStore` (the timing wrapper around the store in every workload) now passes cleanup calls through. |

Existing workloads are reused unchanged: P-01, P-02, P-08a/b/c (G-1), and P-04, P-05, P-06r, P-06s, P-09 (G-2).

The P-10 verdict follows the plan. It compares the median post-GC heap in the last quarter of the run with the first
quarter (for 24 h: the last 6 h against the first 6 h). It passes at 110 % or less. Live caches (attempt entries and the
scope map) must not grow with the number of finished jobs. A run shorter than 24 h is always marked as a smoke run.

SQLite and Redis were not run. The workload runner only drives PostgreSQL, and adding the other stores is not cheap.

- P-07: copying 100,000 jobs took 9 minutes here. At that speed 1,000,000 takes about 1.5 hours per repetition.
- P-10: the soak reconciles job counts with what cleanup deleted and what the scheduler created; no job was lost.

## What you need to run on a dedicated quiet host

Host per the plan: a Linux x64 worker host with 4 vCPU / 8 GiB, a separate PostgreSQL 18 host with 8 vCPU / 16 GiB on
local SSD/NVMe, network RTT at most 1 ms, nothing else running. Docker on the worker host (P-08c starts its own
container to kill and restart). Record the image digests and the commit; `env.json` in each case folder captures most
of it.

One command runs the whole qualification, full profile, every case, then the 24-hour soak at 70 % of the P-02 rate
measured in the same run:

```bash
SP029_PROFILE=full SP029_REFERENCE=1 \
SP029_PG='Host=<db-host>;Port=5432;Username=postgres;Password=<pw>;Database=postgres' \
eng/run-sp029.sh artifacts/sp029/reference-$(date -u +%Y%m%d)
```

Expect roughly 15 to 20 hours for the measured cases (three repetitions of 5 + 15 minutes for P-01, P-01t, P-03 and P-07,
the P-02 ramp, the 1,000,000-job copy three times) plus 24 hours of soak plus drains. To split it into two sittings:

```bash
# 1. every case except the soak
SP029_PROFILE=full SP029_REFERENCE=1 SP029_PG='...' \
SP029_CASES="P-01 P-01t P-02 P-03 P-04 P-05 P-06r P-06s P-07 P-08a P-08b P-08c P-09" \
eng/run-sp029.sh artifacts/sp029/reference
# 2. the 24 h soak; take the rate from step 1: 0.7 × sustainableRate in artifacts/sp029/reference/perf/*-P-02/result.json
SP029_PROFILE=full SP029_REFERENCE=1 SP029_PG='...' SP029_SKIP_BUILD=1 \
SP029_CASES=P-10 SP029_SOAK_MIN=1440 SP029_SOAK_RATE=<rate> \
eng/run-sp029.sh artifacts/sp029/reference-soak
```

Leave out `SP029_PG` to run against a local container instead; then record that the database shared the worker host.
Keep the whole output folder: the raw results are the evidence. The verdicts are in `summary.md`.

Things to watch on that run:

- P-07 and P-10 load the whole store into memory for the correctness check at the end. With 1,000,000 jobs this needs a
  few GB on the worker host.
- P-04's full profile counts 10,000 admissions per variant, as the plan asks.
- P-09 runs at 100/s offered in the full profile. If the relay stays near 25/s there too, the run will spend most of its
  time draining (bounded at 90 minutes, then it is reported as a run failure, not a violation).

## Threshold revisions

Decided by the owner on 2026-11-09: P-06 takes option (b) below, and the defaults stay as they are. The rule is now
"p99 ≤ schedules ÷ JobsPerSecond + 3 s", which is 13 s for 1,000 schedules at the default 100 per second. The workload
(`G2Workloads`, which records the bound as `lagBoundS`), `eng/sp029-summary.py`, spec 13, spec 15 and the performance
acceptance plan use it. This run's 52 s still misses it. P-09 is unchanged until the reference run.

The proposals as first written:

1. **P-06 scheduler lag p99 ≤ 3 s with 1,000 minute schedules.** All 1,000 schedules fall due in the same second each
   minute. The scheduler's default allowance is 100 jobs per second (`SchedulerOptions.JobsPerSecond`, burst 32). So the
   last occurrence of each minute waits at least 10 s by design, before any database time. The p99 cannot be under
   about 9.9 s with the defaults. Here it was 52 s. Options:
   - (a) run P-06 with `JobsPerSecond` ≥ 1,000 and keep 3 s. That is a profile change: record it as such.
   - (b) keep the defaults and make the rule "p99 ≤ schedules ÷ JobsPerSecond + 3 s", which is 13 s for this workload.
   - (c) spread the 1,000 schedules over the minute (different second fields) and keep 3 s.
2. **P-09 relay ≥ 100 deliveries/s with four relay slots.** Each slot makes one store Dispatch and one source mark per
   message. 100/s from four slots needs each cycle in 40 ms or less. Here it was about 170 ms (23.6/s); the PF runs
   saw 26/s. On a 1 ms network this may get there, so I suggest waiting for the reference run. If that run also misses,
   the choice is (a) more relay slots in the reference profile (16), (b) batched Dispatch in the relay, or (c) a lower
   target with the measured cycle time stated.

Not a revision request, but worth knowing: P-07's "throughput degradation ≤ 20 %" is only meaningful when P-01 runs
near its limit. On a host where P-01 easily keeps up with 100/s, both windows finish 100/s and the check always passes.
The latency of the finishes is a stronger signal there; it is recorded in the result file.

## What I did not do or check

- No SQLite or Redis runs (the runner is PostgreSQL only).
- No reference-host result, no full profile, no 24-hour soak.
- The P-09 seven-day cutoff stays "not run", as in G-2.
- The harness `TimingStore` keeps two small per-attempt maps that are cleared on finish. If a finish is never applied
  (for example a lost lease), its entry stays. It did not show in the 10-minute soak (heap ratio 0.999). Watch it in
  the 24-hour run.

## Follow-up: the P-07 viewer error (2026-11-09)

The one P-07 viewer error came from the end of the run, not from load.

When the workload stopped its viewers at the end of the measurement window, one viewer was in the middle of a read. The PostgreSQL and SQLite stores report a cancelled operation as "not applied (store_unavailable)". The management session then passed that on as `StoreUnavailableException`.

The call counts show it:
- `listJobs` succeeded 721 times.
- The other three reads succeeded 720 times each.
- There was exactly one error.

**The fix:** a management read whose caller cancelled now ends as a cancellation.
- Code: `src/Runwick/Management/ManagementSession.cs`.
- Test: `ManagementContractTests.A_read_the_caller_cancels_is_a_cancellation_not_an_unavailable_store`. It fails without the fix with the same error.

P-07 has not been rerun since the fix; the reference run will show it.
