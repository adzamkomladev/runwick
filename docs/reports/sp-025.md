# SP-025: Redis store (partial)

Branch `worktree-agent-aacf0198e855f1f18`, built on `b1260ad`. Status: **partial, not ready to tag**. The core job protocol runs on
Redis and passes the shared contract suite. Controls, management reads, rates, scaling, schedules, outbox receive and retention
are not built yet. The "What is not done" section below lists them.

## What was built

`src/Runwick.Redis` is a new package. It talks to one Redis primary through StackExchange.Redis 3.4.20, as spec 22 describes.

- **One Lua script per operation.** Each operation is a single script. Every script shares a prelude and a jobs library. A write
  script does these things in order inside one script call:
  1. checks the gates;
  2. reads the Redis clock;
  3. looks up the receipt;
  4. makes the decision on an in-script copy of the data;
  5. stores the planned changes ("the intent") in the application's `meta` hash;
  6. applies up to 100 of those changes;
  7. publishes by bumping the application revision and clearing the guard.

  Scripts are sent by SHA. When Redis answers NOSCRIPT, the client loads the script and sends it once more.
- **Recovery.** If a script stops part-way through, a guard stays set in `meta`. A reader that sees the guard gets
  "Recovering". The next writer finishes the stored intent with the recovery script, 100 changes per call, and then sends its
  own command again. Nothing ever deletes an intent.
- **Operations built:**
  - Register application, queues and scopes
  - Dispatch and DispatchMany, including active and window uniqueness keys and scope seeding
  - Reserve, Begin (with the rate step and deferral), Renew, RenewMany and ReserveAndBegin
  - Finish, FinishMany (each item keeps its own receipt), Recover and ReleaseReservation
  - ResolveCommand
  - ReadinessProbe/2, ListExpiredLeases, ListUnsupportedBacklog and PublishPresence
- **Describe and the checks around it.** Describe reads `rw:store` and runs the profile check: the five config settings, the
  role, the mode, the AOF state, the version (8.2 or later) and the module list. It checks the layout revision and the manifest
  digest, then reads the application gate. The profile check runs again on a timer (every 30 s by default, allowed range
  5 s to 5 min) and after every reconnect. The history check (store identity, and no revision lower than one this process has
  already seen) runs whenever Redis's `run_id` changes.
- **Migrator.** `RunwickRedisMigrations.MigrateAsync` does the following, in order:
  1. runs the profile check;
  2. takes a lock in Redis;
  3. refuses to run if any `rw:*` keys exist without `rw:store`;
  4. writes `rw:store` once (store id, layout 1, manifest and digest).

  Running it again is a no-op.
- **Builder.** `UseRedis(configuration, options)`. It refuses several endpoints or a Sentinel service name
  (`topology_unsupported`). It keeps only the endpoint, credentials, TLS, database and connect-timeout settings from the
  configuration string.
- **Harness.** The harness gains `StoreKind.Redis`. All fixtures share one server, and each fixture uses its own application
  namespace, removed when the fixture is disposed. The harness connection string for Redis is `redis|<configuration>`, used by
  `TestClient` and `WorkerHost`. A `RedisSnapshotReader` builds the ReferenceModel snapshot from the job, attempt, permit,
  dispatch-key and receipt records. Because of this, every existing contract theory now also runs on Redis.

## Deviations from the spec

- **One extra sorted set per concurrency scope,** `permits:<scopeId>`, alongside the `permits` hash. It lets the script count
  live permits without scanning the hash.
- **Flat job hash.** Generation and attempt fields live in the job hash as `g:<n>:<field>` and `a:<attemptId>:<field>`, not as
  separate keys. A job's state then changes in one key.
- **Retry jitter.** The client sends a uniform draw in [0, 1), and the script applies the equal-jitter formula to it.
  PostgreSQL takes 64 bits of entropy modulo the range. The distribution is the same; the arithmetic is not bit-identical.
- **No new exception type for Recovering.** A write that cannot finish recovery throws `StoreOutcomeUnknownException("store_recovering")`.
  A read throws `StoreNotAppliedException("store_recovering")`.
- **FinishMany confirmation marker.** A replayed FinishMany item writes the receipt's confirmation marker directly (as spec 22
  §4.5 does for single commands). That write is not part of any intent.
- **Scheduled-job headers.** A manual trigger's occurrence time is stamped with the client clock, not the script's decision time,
  because the headers are built before the script runs.
- **Limit refusals are not reached by any current operation.** The dispatcher caps a batch at 100 items, which stays under 256
  keys and 1,024 after-images. The `intent_too_many_keys`, `intent_too_many_mutations` and `intent_too_large` paths exist in the
  prelude but are not exercised by a test.

## Step 3: controls, events, management reads, disclosure (added)

Built on `584eaf8`, container `runwick-redis-ctl` (port 56381).

- **Controls.** Cancel, ManualRetry, RerunSucceeded, SetQueueState and EditScopePolicy are one script each
  (`Lua/ops/cancel.lua`, `retry.lua`, `queue_state.lua`, `scope_policy.lua`). Each stores the effect, the event, the audit row and
  the receipt in one intent. A stale position answers `revision_conflict` with `actual=<generation>/<revision>`.
- **ManagementDispatch/1.** Uses the existing dispatch script; the audit row now follows the shared audit-row convention
  (`targetKind`, `targetId`, `resultingRevision`, `details`).
- **EventsSince/1.** Reads the `events` index after the cursor. TxId is always 0 and Partial is always false.
- **Management reads.** One read script (`mread.lua`) serves jobs, job detail, queue-of, command NotAfter, queues, workers, scopes,
  schedules and audit. Job pages walk `idx:created*` newest first and stop when the page is full. A page that would examine more than
  5,000 entries answers a statement timeout, which the session reports as `query_budget_exceeded`.
- **RecordDisclosure/1.** One write script: the audit row and the read are one intent, so a failed write returns nothing.
- **Tests.** `ControlContractTests` and `ManagementContractTests` come from the integration branch and run on all stores. A small
  Redis form of the admin SQL (`RedisAdminSql`) answers their `runwick.*` assertions from the application's keys. Fault-injection
  cases (MGMT-04, MGMT-09, the failing-audit half of MGMT-13) are skipped on Redis; `RedisControlTests` covers them with the
  fail-after-N-writes seam. REDIS-12 covers event tailing under deletion, ListJobs against a reference filter and the 5,000-entry bound.
- **Results (Redis only).** Contract tests 29 passed; Redis tests 14 passed; 0 warnings.

Open points: `ListSchedules` reads the `sched` hash by an assumed row shape (`paused`, `needsReview`, `definitionRevision`,
`controlRevision`, `nextDueAt`, `lastMaterializedAt`) and is tested only when empty; retention must set `detailexp` (ms) on a job
and delete `pay:<id>` when it expires detail.

## Schedules and retention (steps 5 and 7)

Built on top of the core above; the scripts are `Lua/sched.lua` plus `Lua/ops/sched_*.lua`, `cleanup.lua`, `edit_retention.lua` and
`retention_get.lua`; the C# is `RedisStore.Schedules.cs` and `RedisStore.Retention.cs`.

- **Schedules.** All eight operations of `ScheduleOperations.All`, the due read, the schedule read and the store clock. Each schedule
  is one row (canonical JSON) in the `sched` hash, found by `k:<key>`; the current definition is stored as the client sent it, per
  revision (`d:<id>:<revision>`). `sched:due` holds the due schedules by `scan_after_at`. Occurrences live in `occ:<id>`, audit ranges
  in `sched` (`ar:...`) with their own time indexes (`occ:idx`, `sched:ar`) so retention can age them out.
- **Materialization goes through the shared dispatch path.** `MaterializeOccurrences`, `TriggerSchedule` and `ResolveCatchUp` call
  the same `dispatch_core` as Dispatch, in the same script call (created reason `scheduled`). The client builds the dispatch items
  from the schedule it just read, because their digests depend on the command; the script refuses the plan if the revisions it holds
  are not the expected ones. This removes the client-clock deviation listed above: a manual trigger's header times are now written
  by the script from the server clock (the client sends a `"__now__"` marker).
- **Retention.** `CleanupBatch` is one intent per batch, chosen from the indexes: receipts (`rcpt:exp:*`), window keys
  (`keys:window:exp`), events and audit (head of the sorted set), scaling, occurrences, schedule audit, worker presence, outbox
  mappings (`outbox:exp`), rate grants (one scope per batch) and terminal jobs (from `idx:created:s:<state>`, with a cursor).
  A batch deletes at most 100 rows and stops early if its intent would write more than 230 keys. `EditRetentionPolicy` and
  `GetRetention` follow the SQL stores. Progress and the policy are in the `retention` hash.
- **One small change in dispatch.** When a window key is bound to a job, the job hash now records `w:<key>`. Retention needs it to
  find out that a purged-looking job still has a live window binding.

## REDIS-01 and REDIS-07 finished, and status counts (follow-up)

### REDIS-01: a crash at every step, compared byte for byte

New test class `RedisCrashTests` (one theory, one row per operation). It runs on its own Redis container
(`runwick-redis-r01-<random>`, image `redis:8.2-alpine`, the same AOF-always settings as `runwick-redis-sp025`, a free port), which is
removed when the class ends.

For each operation, and for each point where its script can be stopped (after write 1, 2, 3, … up to 30, then every 25th write and
around each 100-write projection batch), the test:

1. builds fresh state and copies every key of the application;
2. runs the command and stops the script after that many writes;
3. kills the server with `kill -9` and restarts it from the AOF;
4. checks that a read answers "Recovering" (the half-written state is never visible);
5. sends the same command again, which finishes the stored intent and replays the reply;
6. builds the **clean run** to compare against: the copied start state under a second application prefix, the same stored intent
   (which fixes the decision time and every chosen ID), projected with no interruption;
7. compares every key, field and value byte for byte, and the raw reply byte for byte, between the recovered and the clean run.

Two things are left out of the comparison on purpose, because the spec makes them differ: the receipt's `confirmed` marker (22 §4.5:
each replay writes it fresh, with its own time), and the reply's "replayed" flag (a resend is a replay by definition). For FinishMany,
the batch has no receipt of its own, so a resend is a new batch call with its own envelope time; its items replay their stored
receipts, and the items are compared.

Already built and still part of REDIS-01: acknowledged dispatches survive `kill -9` during AOF rewrites, and a torn last AOF write
refuses startup until `redis-check-aof --fix` (`RedisFaultTests`). Write-prefix sweeps without a kill cover controls, schedule
materialization and every cleanup class (`RedisPrefixTests`, `RedisControlTests`, `RedisSchedulesRetentionTests`).

**Store bug found and fixed.** After a restart, the client reconnects while Redis may still be loading its AOF. The profile check that
runs on reconnect then got `LOADING` answers (for example to `MODULE LIST`) and recorded them as `store_profile_mismatch`. That closed
admission until the next recheck, 30 s later. The check now waits while `INFO` reports `loading:1` (at most 30 s) before it decides.

### REDIS-07: renewal wait under the largest intents

- **1,024 after-images cannot be reached by any operation.** An intent writes at most two after-images per hash or sorted-set key
  (field deletions, then field sets) and one per string key. Under the 256-key limit this caps an intent near 512 after-images. The
  test therefore runs the largest real intent: a driver-level DispatchMany of 120 jobs.
- The test now measures each intent it runs from the stored intent itself:
  - the background intent: **249 after-images, 248 keys, 168,634 bytes**;
  - the maximal public DispatchMany (100 items mixing active keys, window keys and 33 concurrency scopes): **213 after-images,
    212 keys, 159,921 bytes**, accepted.
- **Measured on this host (non-reference host: shared and loaded), informational only.** Two runs:
  - inside the full Redis suite (other test classes running in parallel): 79 large intents back to back in 20 s; RenewMany(64)
    p50 36.9 ms, p99 636.3 ms; Renew p50 124.3 ms, **p99 733.7 ms**. That run had only 94 samples, so the test now samples until it
    has at least 100 (capped at 120 s);
  - alone: 149 large intents in 20 s, 167 samples; RenewMany(64) p50 22.2 ms, p99 144.9 ms; Renew p50 95.5 ms, **p99 227.9 ms**.
- The 250 ms bound is asserted only when `RUNWICK_REFERENCE_HOST=1`. The reference host is the pass/fail authority; this host's
  number says nothing about it. On other hosts the test asserts that the case runs (at least 5 large intents, at least 100 samples)
  and that the maximal DispatchMany is accepted. The conformance tool needs no exemption row for this: it flags only early returns
  by store kind.
