# SP-028: Driver conformance reports (PostgreSQL, SQLite, Redis)

Built on `8167b4a`. Run on 2026-11-08. **G-4 does not pass for any of the three drivers.** The reports are real and complete; what they show is that
many required cases have no result on SQLite and Redis, and a handful on PostgreSQL. Nothing was loosened to change that.

## What was built

- `docs/conformance/cases.csv`: the case registry (321 rows). Each row says which spec defines the case, whether it is mandatory, whether it applies to each
  driver (applicable, N/A with the spec reason, declared-unsupported, or partial), and which tests cover it. `docs/conformance/README.md` explains the columns and
  every scoping choice.
- `eng/conformance.sh`: runs every test project (engine and host projects once, then the contract suite and the driver's own project per driver with
  `RUNWICK_TEST_STORES`), collecting TRX files under `artifacts/conformance/`. `--rerun` runs one project alone and the report records that a test passed on a rerun.
- `eng/conformance.py` (Python 3, no packages): reads the TRX files and the test source, joins them with the registry, and writes
  `docs/conformance/postgres.md`, `sqlite.md`, `redis.md`. It exits non-zero unless G-4 passes. It fails when:
  - a mandatory applicable case has no passing result;
  - a test is skipped and is not listed in `docs/conformance/exemptions.csv`;
  - a registry case matches no test and is not declared as a gap.
- It also reads the test source to find **theory rows that quietly `return` for a store kind**. Those pass without asserting anything. Three exist, all on Redis
  (MGMT-04, MGMT-09, MGMT-13); they are listed in `exemptions.csv` and are not counted as passes (MGMT-04 and MGMT-09 get their real Redis evidence from `RedisControlTests`).
- New tests for declared-unsupported capabilities (each asserts an explicit error and that nothing was written; trait `Unsupported=<driver>`):
  - PostgreSQL: non-UTF8 database refused by the migrator (`encoding_unsupported`); staging on a read-only caller transaction (`transaction_invalid`).
  - SQLite: store file on a network filesystem (`topology_unsupported`); in-memory and shared-cache stores (`invalid_policy`).
  - Redis: several endpoints and a Sentinel service name (`topology_unsupported`); `appendfsync everysec` (`store_profile_mismatch`); caller enlistment is not offered
    (no staging dispatcher or completion service is registered, which covers TX-01 in its Redis form and TX-02 to TX-04); the CLI refuses `--provider redis` (`usage_error`).

## Results after the gap-closing work (latest run, 2026-11-08)

Three gap-closing branches ported the PostgreSQL-only cases to `Runwick.Contract.Tests`, added the missing Redis-specific cases and fixed about 15 store bugs on the

`eng/conformance.sh` now runs the PostgreSQL `RequiresDocker=true` cases on their own Testcontainers server. These are the restart, outage and clock cases.
They pass that way, so they are no longer reported as failures.

What still blocks G-4:

- **PostgreSQL: DASH-07.** The dashboard smoke test passes in Chromium and Firefox. It cannot run in WebKit here because the machine lacks the WebKit libraries.
- **SQLite and Redis: CLN-05.**
  - The case has no test on these drivers.
  - **Your decision:** either mark it "not applicable" for them (my proposal), or have a test written.
- **SQLite: SQL-08.** The bundled SQLite engine was only loaded and checked on linux-x64. A win-x64 run is owed.
- **Redis: REDIS-01.** Restarts after `kill -9` are built only at the Finish crash points. The byte-for-byte comparison with a clean run and the outbox and presence operations are not built.
- **Redis: REDIS-07.** The 250 ms renewal bound is a reference-host requirement, and the numbers come from this shared host. The largest intent measured had about 240 keys, not the 1,024 the case asks for.

Load-sensitive tests that failed in the full run and passed when rerun alone:
- the Redis misfire and schedule tests, which had stale state on the shared Redis server;

## Things the run found

- **Hidden skips exist:** the three Redis early-return theory rows above. Also the contract theories for SCH-02, SCH-03 and UPG-09 have no Redis rows; a store-filtered
  run reports them as "No data found" failures. The report lists these as "no rows", not as results.
- **Docker-managed server needed:** five PostgreSQL tests (RATE-10 clock test, store restart, and the WRK-08 / scaler / capacity outage cases) skip or fail when `RUNWICK_TEST_PG`
  points at an external server. They were rerun alone with a Docker-managed server and all 13 passed; the report records them as passed on a rerun.
- **Load-sensitive failures, rerun alone and passed:** `An_edit_cuts_over_forward_and_never_rewinds` (250 ms evaluation budget; SQLite and Redis rows) and
  `Events_need_application_wide_read_and_show_actors_only_with_audit_read` (AspNetCore). Both failed once during the full run.
- **Registry fact:** CLI-04 and WV-08 are asserted inside other tests (CLI-01, SER-10), so the registry selects those tests by name.
- **Scoping choices to confirm:** spec 07 and 15 cases that spec 20 §12 and 22 §12 do not list are N/A for SQLite and Redis; RET-01 is applicable to SQLite although spec 20 still says N/A; cases
  whose only tests are in `Runwick.Core.Tests` (fake store) are treated as engine cases and take that evidence; host products (CLI, dashboard, outbox) are verified on PostgreSQL only.

## How to reproduce

`RUNWICK_TEST_REDIS=127.0.0.1:<port> eng/conformance.sh` (needs the PostgreSQL test server and an AOF-always Redis; the script header lists the variables). `eng/conformance.py --check` re-evaluates without writing.
No file under `src/` was changed.
