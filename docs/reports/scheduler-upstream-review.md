# Scheduler architecture review: TickerQ and Quartz.NET

Source review, 2026-11-11. No benchmarks were run and no speedup is claimed. This report supplements `docs/plans/perf-plan-2.md`; it does not authorize implementation or change scheduler semantics.

## What transfers to Runwick

### TickerQ: drain overdue work, bound admission, wake when the schedule changes

The scheduler distinguishes discovery polling from waiting for an already-selected due time. Overdue batches bypass the minimum discovery interval. Zero-delay iterations yield cooperatively; failed publication backs off. A bounded acquired-execution queue admits batches with a capacity wait. Changes arriving across a discovery read are detected with a change counter after the new next-wake plan is published. This directly supports productive-page draining, explicit no-progress backoff and notification race tests in Runwick. It does not justify removing all rate limits or buffering unlimited schedules. [Pinned scheduler loop](https://github.com/Arcenox-co/TickerQ/blob/2ac18b3b38150e52c1bdb5581a43b98aa569b73d/src/TickerQ/Src/BackgroundServices/TickerQSchedulerBackgroundService.cs#L184-L341).

TickerQ's manager concurrently reads earliest cron and time-ticker groups, then combines eligible groups. It filters exact timestamps so sharing a bucket does not permit early execution, and recomputes remaining delay after storage work. Its catch-up path is explicitly conditional: `RunLatest`, skip handling, maximum lateness and provider support. It finds the latest allowed past occurrence with bounded binary search rather than enumerating every second of an outage. These are examples of bounded due discovery and policy-specific recovery, not equivalent semantics to Runwick's catch-up episodes. [Pinned manager](https://github.com/Arcenox-co/TickerQ/blob/2ac18b3b38150e52c1bdb5581a43b98aa569b73d/src/TickerQ.Utilities/Managers/InternalTickerManager.cs#L170-L250), [catch-up selection](https://github.com/Arcenox-co/TickerQ/blob/2ac18b3b38150e52c1bdb5581a43b98aa569b73d/src/TickerQ.Utilities/Managers/InternalTickerManager.cs#L493-L535).

Ownership is a persistence concern: the inspected EF immediate-cron acquisition sets holder, acquisition token and lease fields, then reads back rows matching its token. The presence of local worker concurrency therefore does not itself establish distributed ownership. This observation is scoped to the inspected acquisition path, not a complete audit of every TickerQ provider or failure mode. [EF acquisition](https://github.com/Arcenox-co/TickerQ/blob/2ac18b3b38150e52c1bdb5581a43b98aa569b73d/src/TickerQ.EntityFrameworkCore/Infrastructure/TickerEFCorePersistenceProvider.cs#L1108-L1143).

### Quartz.NET: one acquisition coordinator can feed concurrent execution

The scheduler asks for `min(available worker slots, configured batch size)` triggers. It waits until the next acquired trigger is due, and can release acquired triggers when an earlier schedule change invalidates that wait. This separates acquisition/wake decisions from job execution. A single scheduling coordinator is compatible with concurrent jobs; increasing worker count alone does not fix an acquisition loop that sleeps while backlog remains. [Scheduler thread](https://github.com/quartznet/quartznet/blob/f3ec5fa7476070c1aa20add02ced82499c9e8d4b/src/Quartz/Core/QuartzSchedulerThread.cs#L270-L340).

The task-based pool uses a semaphore to cap concurrent tasks and submits work to a task scheduler. Its concurrency setting is admission capacity, not a request for a corresponding number of dedicated CPU cores. [TaskSchedulingThreadPool](https://github.com/quartznet/quartznet/blob/f3ec5fa7476070c1aa20add02ced82499c9e8d4b/src/Quartz/Simpl/TaskSchedulingThreadPool.cs#L120-L205).

In this Quartz version, persistent acquisition takes the trigger-access lock when configured or when acquiring more than one trigger. Candidate selection is bounded; acquisition conditionally changes a waiting trigger to acquired and records the fired instance. Misfire recovery uses a bounded normal batch, but startup recovery deliberately requests all misfires. Cluster recovery examines failed scheduler records and their fired triggers. Thus larger batches have ownership and lock-duration consequences, and a misfire policy is not merely a performance setting. These details must not be imported as a replacement for Runwick's revision/cursor checks and command receipts. [Acquisition](https://github.com/quartznet/quartznet/blob/f3ec5fa7476070c1aa20add02ced82499c9e8d4b/src/Quartz/Impl/AdoJobStore/JobStoreSupport.cs#L2608-L2760), [misfire handling](https://github.com/quartznet/quartznet/blob/f3ec5fa7476070c1aa20add02ced82499c9e8d4b/src/Quartz/Impl/AdoJobStore/JobStoreSupport.cs#L740-L780), [cluster recovery](https://github.com/quartznet/quartznet/blob/f3ec5fa7476070c1aa20add02ced82499c9e8d4b/src/Quartz/Impl/AdoJobStore/JobStoreSupport.cs#L3391).

## Concrete Runwick direction

Local source observations: `SchedulerService.LoopAsync` reads one due page, awaits each `MaterializeOneAsync` in sequence, and then waits even after productive work. The defaults are a 32-schedule page and a one-second productive poll interval. For 1,000 already-due, one-occurrence schedules, 32 pages imply 31 intervening waits, roughly 31 seconds before accounting for SQL, allowance and evaluation. Jitter, notifications and known future due times can alter those waits. This is a code-derived mechanism, not a measurement or a complete explanation of P-06's 52-second p99. See `src/Runwick/Scheduling/SchedulerService.cs:274`, `src/Runwick/Scheduling/ScheduleBuilder.cs:59`, and `ScheduleBounds.DueReadLimit`.

1. **S0 — Split the lag into stages.** Measure due-to-read, evaluation, allowance, materialization command/resolution, and materialized-to-worker-start separately. Record page occupancy, applied versus stale/no-progress results, pending schedules and oldest due age. Reproduce P-06 before changing behavior.
2. **S1 — Drain productive full pages without the ordinary poll sleep.** Immediately request another page when a full page advances durable state; retain cancellation/cooperative yielding, shared allowance and backoff for stale, incompatible, rejected or failed work. A full page alone is insufficient evidence of progress. Test an overdue catch-up schedule mixed with unrelated schedules so repeated first-page work cannot starve the rest. This is the smallest upstream-supported fix to measure first.
3. **S2 — Overlap bounded storage waits across independent schedules.** Keep one due-read coordinator and a bounded materialization pipeline. Start with a small configurable in-flight limit and sweep it independently of worker count. Keep at most one unresolved command per schedule locally, preserve its immutable command ID/body through unknown-outcome retries, and re-read after a stale result. Bound retained payload bytes as well as command count. Centralize allowance admission: the existing mutable token bucket assumes serial access. Preserve the shared evaluator slot initially.
4. **S3 — Group independent durable commands only if remaining cost warrants it.** Bounded grouped transport/transactions may amortize latency, but each schedule still requires its own revision/cursor preconditions and replay identity. Define partial failure and unknown-outcome behavior explicitly; do not silently turn independent operations into an all-or-nothing command or introduce a new receipt contract. Measure lock duration, per-schedule tail latency and commit cost before selecting this over S2.

Runwick's `EvaluatorSlot` intentionally admits one synchronous evaluator call per scheduler/store group, with no replacement while an evaluation is still running (`src/Runwick/Scheduling/Evaluation/EvaluatorSlot.cs:3`). Parallel recurrence computation therefore requires a spec decision and bounded evaluator design; `Task.Run` around the existing single slot cannot make evaluation parallel. Overlapping asynchronous database waits can improve utilization without changing that evaluator policy. CPU-bound job handlers can use multiple cores through worker concurrency; scheduler materialization concurrency, evaluator concurrency and worker concurrency must remain separate controls.

Adding scheduler processes without partitioning selection can have each process plan the same due schedules and lose on stale cursor checks. Measure duplicate reads/plans and stale-command rates before treating more nodes as scheduler scaling. Preserve store-side concurrency checks and occurrence uniqueness; partitioning or leases would need explicit ownership, failover and fencing semantics rather than copying a library's worker-count setting.

Acceptance should retain P-06 p99 ≤ 13 seconds, measure isolated materialization lag as well as end-to-end job start, and cover synchronized bursts, steady arrivals, long outages under every misfire policy, earlier schedule edits during sleep/read, listener loss, two competing scheduler nodes, store failures and unknown replies. Report observed gains only after paired measurements. The source review establishes design options, not throughput rankings.
