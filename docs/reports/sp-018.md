# SP-018 report: Redis store prototype

Date: 2026-11-08. Branch: `claude/loving-yalow-dc7e90` (not merged; tag `sp-018` only after merge).

## Decision: go

The Redis design in [redis-design-closure.md](../architecture/redis-design-closure.md) works as written. SP-025 can build the full Redis provider on it, with the selected profile `redis-aof-always-single-primary-v1`.

All six acceptance cases (REDIS-01 to REDIS-06) passed against a real Redis 8.2 server with `appendonly yes` and `appendfsync always`. Failures were injected after every write. No authoritative read ever showed a half-written command: a read either showed a fully published state or said "Recovering".

Nothing found needs a weaker profile or a change to what an acknowledgement means. Four things must be carried into SP-025 (listed under "What SP-025 must do"). Three of them need small spec additions, listed under "Spec changes needed".

## What was built

A prototype store, about 650 lines: Lua scripts plus a thin C# client. It lives in the test project because it is not shipped. SP-025 builds the real `src/Runwick.Redis`.

Operations covered: Dispatch, DispatchMany, Reserve, Begin, Renew, Finish, Recover, a schedule fire (job + schedule cursor + outbox message + audit row in one command), and an outbox append with audit.

### How a write works

1. One Lua script reads the current state, checks the store ID, receipt, NotAfter and ownership, and takes the decision using the server's clock.
2. Its first write stores the whole decision in the application's meta hash: the guard (the command ID) plus every after-image, as a single `HSET`.
3. It then writes the after-images (job hashes, indexes, counters, the receipt) and finally clears the guard and bumps the application revision in a single `HSET`.
4. Every read and every write checks the guard first. If the guard is set, a read answers "Recovering". A write first finishes the pending intent and then runs.
5. Finishing an intent means re-writing its after-images. They are absolute values, so writing them twice is harmless: no counter is incremented twice and nothing is redrawn.

Small commands (up to 100 mutations) do all of this in one script call. Large ones are accepted in one call and projected in batches of 100 mutations per call.

All keys of an application share one hash tag, `rw:{app}:…`, so they stay in one slot.

## Results

Server: `redis:8.2-alpine@sha256:fe9daae35cd4fd6ec22416aa4fe0cf6b3e36741e06ff45b9986253fe2a81c041` (Redis 8.2.11), started through Testcontainers 4.16.0. Client: StackExchange.Redis 3.4.20 with no offline backlog (`BacklogPolicy.FailFast`) and 2-second timeouts. 19 tests, all passing; the suite takes about 2.5 minutes.

### REDIS-01: every write prefix, crash and restart: passed

- 10 operations, each interrupted after every write: 109 interrupted states, including "everything written but the reply lost". In 65 of them the raw keys really were half-written; reads hid all of them.
- All 109 states were then crashed with `kill -9` together and restarted from the AOF. Every partial write was still there exactly as before the crash, still hidden.
- Resending each command (what a caller does after an unknown outcome) finished the intent. The result was byte-for-byte the state and reply of a clean run.
- Large intents (120 jobs, projected in batches) were interrupted at 7 points, including between batches and inside a two-write after-image. Same result.
- 547 acknowledged dispatches all survived a `kill -9` during load while three AOF rewrites ran. The 4 commands in flight were resolved by resending them.
- A torn last AOF write: the server refused to start (`aof-load-truncated no`), so the profile became unavailable. After the operator ran `redis-check-aof --fix`, the torn command was gone as a whole and the earlier 19 were intact.

A finding that confirms the design: when a Lua script fails halfway, Redis keeps its earlier writes and also writes them to the AOF. A plain multi-write script therefore leaves visible half-commands (the test shows one). The intent and guard are what make this safe.

### REDIS-02: persistence errors and lost replies: passed

- Lost reply: resending the same command returns the recorded result. The same command ID with a different body returns `CommandConflict`.
- Acknowledged result, then `kill -9`: the result is there after restart. The confirmation marker (a fresh write whose reply only comes after fsync) succeeded and survived a second crash.
- Disk full (a 4 MiB tmpfs): Redis 8.2 logged "Short write … Can't recover from AOF write error when the AOF fsync policy is 'always'. Exiting…" and stopped **before replying**. The client saw an unknown outcome. After the space was freed, Redis restarted cleanly: it had trimmed the short write itself. The 10 acknowledged commands were intact, the unacknowledged one had left nothing, and resending it applied it once.

### REDIS-03: expired commands and reconnect: passed

- A command past its NotAfter: `CommandExpired`, no effect, and resolution says "not applied".
- A frozen server (`docker pause`): the command sat in the socket, the client timed out, and the server ran it after its NotAfter. The server rejected it by its own clock, and resending it was rejected too. Nothing was reserved.
- Server down: the client failed at once with "not applied" (no offline queue). After the restart, nothing ran late.
- A Begin accepted while the lease was valid, but published after the lease expired: the replayed Begin is historical. The worker's fresh Renew is refused (`lease_expired`), so no handler starts, and Recover moves the job to retrying.

### REDIS-04: limits, memory, key types, counters, pressure: passed

- Too many keys (300 jobs in one command) and too many bytes (5 MiB of payload) are rejected before anything is written. 250 jobs (254 keys, 503 mutations) is accepted.
- A protocol key overwritten with the wrong type: the command fails after its intent is stored. The application then answers "Recovering" to everything until an operator repairs the key; after that, recovery publishes and work continues.
- Memory full: new commands are refused before they run (the scripts declare that they write, so Redis checks memory first). An accepted intent that cannot be finished for lack of memory keeps the application "Recovering". Raising `maxmemory` lets it finish. The intent is never deleted.
- Counters: Lua numbers are doubles, exact only up to 2^53. The prototype counts in decimal strings: it is exact past 2^53 and refuses (`counter_limit`) to pass the int64 maximum.

Speed on this development machine (not the reference host; fsync on every write):

| Command | p50 | p99 |
|---|---|---|
| Dispatch | 5.2 ms | 17 ms |
| Reserve | 5.5 ms | 17 ms |
| Begin | 5.7 ms | 26 ms |
| Renew | 5.0 ms | 16 ms |
| Finish | 5.6 ms | 18 ms |
| DispatchMany with 250 jobs (3 batches) | 102 ms | 122 ms |
| Renew while 250-job commands run | 97 ms | 122 ms |

On the server, scripts took 0.8 ms on average and none passed the 10 ms slow-log threshold. Almost all client time is the fsync.

The last row is the one to watch. The guard covers the whole application, so a Renew waits while a large command is being projected. With 30-second leases, 120 ms is harmless, but the wait grows with the size of the largest command allowed.

### REDIS-05: wrong topology or configuration: passed

- The selected profile passes the check.
- These are rejected: a replica, `appendfsync everysec`, the image defaults (no AOF), and `allkeys-lru` eviction.
- CONFIG blocked by an ACL (as managed services often do): every setting is "unverifiable", so the profile is unavailable.
- After a restart the server's run ID changes. Admission resumes only if the store ID is the same and the revision has not gone backwards. A server that answers PING but has lost its data (FLUSHALL, or re-registered from empty) is refused.
- A store with a different store ID is refused (`store_identity_mismatch`).

A finding: the official `redis:8.2` image ships with modules (search, JSON, bloom). If you remove CONFIG with `--rename-command CONFIG ""`, the server crashes at startup: RediSearch asserts and the process exits with code 139. Hiding CONFIG therefore has to be done with ACLs, or with an image built without modules.

### REDIS-06: schedule, outbox and audit go through the same protocol: passed

- 8 workers, each on its own connection, ran 1,200 mixed commands at once: schedule fires (often two racing for the same slot), outbox appends, dispatches, and reserve/begin/finish.
- One command in five had a failure injected at a random write; 188 unknown outcomes were resolved by resending.
- A reader ran alongside. In 467 reads, 136 said "Recovering". Every other read was a whole revision: counters matched the indexes, and outbox and audit counts matched.
- At the end, the schedule's fire count equals the fires callers saw applied (134). Audit and outbox rows equal fires plus appends, and the number of created jobs equals fires plus dispatches.

## What SP-025 must do

1. **Bound how long a large command holds the application.** Pick a maximum per command (by job count or bytes) so that renewal waits stay small, and measure it on the reference host. The design already allows this ("optimize batching… without changing the acknowledgement contract").
2. **Count with exact int64 arithmetic in Lua** (decimal strings, as in the prototype) and refuse values past the int64 maximum. Never use `HINCRBY` for after-images, because reapplying it would count twice.
3. **Take decisions inside the script with the server's clock.** The prototype does this, and it gives "fresh time after locks" for free. The decision time is stored in the intent, so recovery after NotAfter publishes the original decision, not a new one.
4. **Record which modules the qualified server runs,** next to the image digest. Treat a CONFIG that cannot be read as "profile unavailable" (as the prototype does).

## Spec changes needed (proposed 2026-11-08, for SP-025)

These are not applied here; SP-025 makes them with the provider.

- **03 §2.1 / §9:** add a store-level "Recovering" outcome for Redis. Every read and command can return it while an intent is pending. It is neither a decision nor "not applied". The public API already has `Recovering` in `DispatchResolutionStatus` (01).
- **03 §9.3:** add stable codes: `intent_too_many_keys`, `intent_too_large` and `intent_too_many_mutations` (InvalidRequest, written before any write), and `counter_limit` (InvariantFault, no effect).
- **Redis design, "declared keys":** a script cannot list its keys in advance when it picks the job from an index (Reserve, Recover). The 256 limit should read "distinct keys an intent writes", all under the application's hash tag. The prototype enforces it that way.

## Not covered

- Real Cluster or Sentinel. Only the INFO checks that reject them were written; they ran against a standalone server and were not tested against a real cluster.
- Disk I/O errors other than "disk full" (for example EIO on fsync), and network partitions longer than a pause.
- Rate grants, permits and fences, uniqueness windows, cancellation, and the receipt-retention cleanup. The prototype covers the intent and publication protocol, not the full command set.
- Numbers on the reference host. The timings above are from a shared development machine.

## How to run

```bash
dotnet test tests/Runwick.Redis.Prototype.Tests --logger "console;verbosity=detailed"
```

It needs Docker. The disk-full case needs root to mount a small tmpfs and is skipped otherwise. The tests run one at a time because several of them kill and restart their server.
