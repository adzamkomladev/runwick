## Where the build differs from or adds to the spec

These are recorded in the Changes lists of 19 and 16 (dated 2026-11-08):

- **No `management_dispatch_v1` SQL function.** Dispatch runs as ordinary SQL statements, like the other management controls: the dispatch core statement, then setting `actor_id` on the `dispatched` event, then the audit insert, all in one transaction. As a result, 0017 only replaces the audit operation check, now `management_audit_operation_v7_ck`. It drops v5 and v6 with `IF EXISTS` and also lists the retention operations, so it applies after 0016.
- A management dispatch's job ID is derived from the command ID, and no trace context is stored, so a resend matches the original exactly.
- Events: a `limit` above 1,000 is clamped rather than refused. An empty page returns the input cursor (or `"0.0"`).
- CLI choices: no colour; `--url` with no context means bearer; `context add --url` is that command's own option (a bug found by CLI-03 and fixed); `describe` works in every mode; `doctor` failures are `check_failed` with the checks still in `result`; a reveal's `commandId` exists only locally; `events tail --limit` is the page size.
- Bugs found by the tests and fixed: a request path like `jobs:dispatch` was read as a URI with scheme `jobs`; `audit list` did not show `commandId` in human output.
- Test harness: the template database name can now be set with `RUNWICK_TEST_TEMPLATE` (default `rw_template`). Parallel test runs on one server were dropping each other's template. My runs used `rw_template_sp032`.

## Follow-up: the SQLite half of `migrate` and `doctor` (2026-11-08)

Done after SP-019's partial merge, on branch `worktree-agent-ae38f3cdab8b82db1`.

- `migrate --provider sqlite` runs `RunwickSqliteMigrations.MigrateAsync`. Its error codes reach the CLI unchanged. `store_unavailable` and `migration_lock_timeout` exit 4 and are retryable; every other code exits 1.
- `doctor --provider sqlite --connection-env …` opens the database file without creating it, and changes nothing. It runs the store's own checks: engine version, `journal_mode`, filesystem topology, then the store revision, `migration_mode`, and whether the file's `runwick_` objects equal this CLI's. `store.settings` is `pass` only when the file is in WAL mode on a known local filesystem. It is `unverified` when the filesystem type is unknown, and `warn` when the store has not been migrated yet.
- The CLI now references `Runwick.Sqlite`, as 19 §1 says. `eng/package-graph.json` allows that edge, and `Runwick.Sqlite` gives `InternalsVisibleTo("Runwick.Cli")`. No new package. `eng/check-package-graph.sh` passes.
- New tests in `tests/Runwick.Cli.Tests/CliSqliteTests.cs` (CLI-08, SQLite half, 3 tests). They run the CLI in-process on real files with no server:
  - `migrate` on a new file applies 3 phases. Run again, it applies none and keeps the same store ID.
  - `doctor` passes and reports revision 1. On a missing file it fails with `store_unavailable` and does not create the file. A store one revision ahead fails with "CLI older than store". An extra `runwick_` index fails as `schema_incompatible`. A file with only application tables gets `warn`, "run migrate".
  - Error codes and exit codes: an in-memory database is `invalid_policy` (exit 1, not retryable); foreign `runwick_` tables are `schema_not_empty` (exit 1); a file in a missing folder is `store_unavailable` (exit 4, retryable); an unset variable is `credential_missing` (exit 5); no connection option is `usage_error` (exit 2).
- Single-file publish smoke test: `eng/smoke-cli-publish.sh`. It publishes `Runwick.Cli` self-contained for linux-x64, checks that no DLLs sit next to the binary, then runs `version`, `--help`, and a SQLite `migrate` and `doctor`. The SQLite run proves the native library is extracted and loads. It passed (binary 77 MB, about a minute with packages already cached). It needs the linux-x64 runtime packs, from the NuGet cache or the network. It is a script, not part of a test suite.
- Side effect: the publish adds `net10.0/linux-x64` sections to the `packages.lock.json` files of the CLI and the projects it references, and the next ordinary build removes them again. They are not committed. So a locked restore (`CI=true`) of `-r linux-x64` would fail until those sections are committed.

Run: all 13 tests in `Runwick.Cli.Tests` passed (the 10 PostgreSQL ones against `runwick-pg`, template `rw_template_sq_cli`, plus the 3 SQLite ones).

Notes:
- The single-file binary is called `Runwick.Cli`, not `runwick`. Only the dotnet tool package installs the command as `runwick`. Rename it with `AssemblyName` if the binary should match.
- There is no `--version` flag. The command is `runwick version`, as 19 §2 lists.
- SQLite `migration_lock_timeout` is not tested, because it needs another process to hold the write lock for 60 s. `migration_checksum_mismatch` is not tested from the CLI either. Its test hook is a static setting that would leak into other tests running in parallel.
