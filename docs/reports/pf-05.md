# PF-05: server functions

Date: 2026-11-02. Branch `pf-05-server-functions`, from main `eb80422`. Spec: "Changes (2026-11-02, PF-05)" in 03, 04 and 07. Proposal: docs/proposals/pf-05-server-functions.md (decisions in §11).

## What changed, in one paragraph

Before, the driver sent each step of a store operation to PostgreSQL as its own SQL statement. It waited for each answer before sending the next one. Each wait is a *round trip*: one message to the server and one answer back. Now each hot operation is one *server function*: a PL/pgSQL program stored in the database. The driver sends one batch, `BEGIN` + timeouts + `SELECT * FROM runwick.<op>_v1(...)`. Then it sends `COMMIT` (or `ROLLBACK`). That is **2 round trips per operation**. The function runs the same statements, in the same order, with the same locks and checks. Replies, error codes, receipts, fencing and `synchronous_commit` are unchanged.

## The numbers

**A job's life (Dispatch + Reserve + Begin + Finish) now costs 8 round trips instead of 21.**

PERF-01 counts the SQL commands of each call (COMMIT not counted). These counts are exact, not measurements.

## 2. How it works (short)

- **One migration, no switch.** Migration `0009_functions` makes schema revision 9. There is no old path to fall back to ("stop-and-migrate"). The protocol (operation names, versions, replies) does not change.
- **One reply shape.** Every function returns one row of type `rw_reply_v1`: status, error code, decision time, and the receipt JSON. The driver decodes a fresh reply and a replayed one the same way.
- **Fresh time after locks.** Each function reads the clock once, after its last lock, as before.
- **Values drawn in SQL.** Attempt IDs (UUIDv7) are built in SQL. Random draws (retry jitter, defer jitter) still come from the client and are sent as arguments.
- **Fault hooks.** Tests inject faults at points inside a function through `rw_fault` lines. Only the test variant of the migration keeps those lines. Production migrations strip them. A production binary refuses a store migrated with hooks (`schema_incompatible`, detail `fault_hooks`). Startup checks a digest of every function body.
- **MaterializeOccurrences.** Its job items need digests that only the C# code computes. So the client still builds them, from the schedule definition at the plan's revision. A definition never changes within a revision, so the driver caches it from the schedule reads that come before a plan. The function checks the plan against the locked row before it uses the items. Items built from the wrong revision are never used.

## 3. Floor: isolated calls (p50 ms, n = 100)

*Non-reference host*: a shared 8-vCPU KVM guest with other agents' builds and tests running. Each run used its own Testcontainers `postgres:18`, reached at the container IP (docker-proxy not in the path). Runs were interleaved: main, PF-05, main, PF-05. "Main" is the Workloads binary built from `eb80422`. "PF-05" is the one built from `f3497db`. Output: `artifacts/perf/pf05-ab-{main,pf05}-{1,2}`.

| Operation | main r1 | PF-05 r1 | main r2 | PF-05 r2 |
|---|---|---|---|---|
| select1 (one round trip) | 3.90 | 2.99 | 4.62 | 1.85 |
| Dispatch | 48.3 | 68.6 | 73.0 | 57.4 |
| Reserve | 52.8 | 69.3 | 65.3 | 42.2 |
| Begin | 39.3 | 41.4 | 49.1 | 26.9 |
| Renew | 26.4 | 32.5 | 49.6 | 32.9 |
| Finish | 49.1 | 43.7 | 60.4 | 30.1 |
| Load average (1, 5, 15 min) at start | 12.0 16.6 16.4 | 8.9 14.3 15.3 | 19.2 19.9 17.6 | 22.7 25.1 22.3 |
| Load at end | 9.3 14.5 15.4 | 19.8 20.0 17.6 | 24.2 25.5 22.4 | 11.5 12.0 15.4 |

**No latency claim is made.** On this host one round trip costs about 2–5 ms, but a call costs 27–73 ms. Most of a call's time is spent waiting for CPU on a busy host, not on the network. Saving 3 or 4 round trips is smaller than the run-to-run spread. In round 2, PF-05 is faster on every call, but the load also fell during that run. A reference host (idle, separate client and server) is needed to measure the latency gain.

## 7. Not done, and why

- **Controls and rate-policy administration** (Cancel, SetQueueState, EditRatePolicy, and the other control commands) stay on statements. This was decided in §11. They are not on a job's path.
- **The other schedule commands** (register, set state, update, trigger, resolve catch-up, evaluation failure, revalidate) stay on statements. They are rare and not on a job's path. They call the same dispatch function as one statement, so there is still one dispatch implementation.
- **No latency result.** This host is shared and loaded, so the floor latencies are noise (section 3). A reference-host run is still needed.
- **The hosted-scheduler flake** (section 6) also fails on main. It is not fixed here: it is a test race, outside PF-05's scope.
