# SP-019 acceptance report: SQLite store

Date: 2026-11-08. Branch: `worktree-agent-a1d844dd0a79fd052` (not merged, not tagged).

## What was built

Spec 20-sqlite.md, first build. Runwick can now run on one SQLite file on one host. The worker engine dispatches, claims, runs, retries and finishes jobs on it, the same as on PostgreSQL. SQLite keeps its own schema revision line, which starts at revision 1.

| Part | Where |
|---|---|

**Bundled SQLite version.** Microsoft.Data.Sqlite 10.0.14 uses SQLitePCLRaw.bundle_e_sqlite3 2.1.13, which ships SQLite **3.53.3** (source id `2026-06-26 20:14:12 d4c0e51e4aeb96955b99185ab9cde75c339e2c29c3f3f12428d364a10d782c62`). That is above the spec's minimum of 3.38. A test read the version at runtime (SQL-08). Native file hashes: linux-x64 `libe_sqlite3.so` sha256 `b0f5c480…c18a07`, win-x64 `e_sqlite3.dll` sha256 `b7385d72…1111fb2e`. Only linux-x64 was loaded and run here.

## Where the build differs from the spec

All of these are recorded in 20 "Changes" (2026-11-08).

- **Lock wait has a 1 s floor.** Microsoft.Data.Sqlite retries a busy statement until its command timeout (1 s), so a command waits max(`WriterBusyTimeout`, about 1 s) before the runner sees "busy". This is why SQL-02 holds the lock for 1.5 s.
- **ReserveAndBegin and FinishMany run one item at a time.** Each still runs in a single transaction with a single commit. Only DispatchMany uses multi-row statements.
- **No wake notifications on SQLite.** Workers poll for new jobs.
- **The Peer picks SQLite by connection string,** not by a `--store` flag.
- **Existing PostgreSQL suite classes were not moved** into the shared project. New contract tests were written for both stores instead.

## Not done (named gaps)

- `ManagementDispatch/1` and retention cleanup on SQLite. Their PostgreSQL versions are being built in parallel. `ManagementDispatch/1` is left out of the SQLite manifest until it exists.
- Other operations not yet on SQLite: controls (cancel, retry, queue state, scope edits) and `EventsSince`, rate limits, schedules, scaling, outbox receive, management reads and `RecordDisclosure`. A host that needs them should stay on PostgreSQL for now.
- The caller-transaction API (§8): `ISqliteJobDispatcher` and `ISqliteJobCompletion`. The internal pieces (`StageDispatch`, `StageDispatchMany`, `StageFinish`) exist. The public classes and the `transaction_profile_mismatch` checks do not.
- Cases not run: SQL-03 (caller transactions), and the TX, RATE, SCH, OUT, EVT and MGMT-13 cases on SQLite.
- win-x64 was not run.
