## Fixes found while testing

- Stage savepoint rollback (product, 2026-11-01; found by the SQLite review, present in both adapters). `StageAsync` rolled back to its savepoint only for provider, conflict and staging exceptions, and passed the caller's token to that rollback. A token cancelled after the INSERT therefore skipped the rollback. On SQLite the staged row stayed in the caller's transaction and committed as `pending` with the business rows. On PostgreSQL the caller's transaction was left aborted (25P02). Now `OutboxStager.RollBackToSavepointAsync` runs on every exception, without the token. It swallows a rollback failure on a transaction the provider has already ended, so the original error surfaces. Test: `SavepointTests` (TX-03). It failed on the old code and passes on the new.

- The SQLite source used `BeginTransaction(deferred: false)`. It now uses `BeginTransactionAsync` (CA1849), and the call sites use the `ConfigureAwait` await-using form (CA2007).
- `StagingTests` (test only): OUTBOX-01, TX-01 and TX-02 compared absolute row counts with values another relay or a previous step had already changed. They now compare before and after.
- TX-04 (test only): `ArmCommitReplyDrop` is started, not awaited, before COMMIT.
- OUTBOX-06 (test only): the test restarted a stopped relay. `OutboxRelay` cannot be restarted after `StopAsync`, because its cancellation sources are readonly. The test now disposes it and opens a new host. This is recorded as a limit.

## Limits and owed

- P-09, the outbox throughput measurement (≥ 100 deliveries/s, p99 ≤ 2 s; 14 §9.4), has not been run.
- The §7 hash-domain golden vectors are frozen (2026-11-01) in `tests/vectors/wire/outbox.json` and checked against both sources.
- SQLite async savepoint review (2026-11-01, Microsoft.Data.Sqlite 10.0.14). The async savepoint calls are the `DbTransaction` defaults: they check the token, then run synchronously. That makes them safe across awaits on one connection. One defect was found and fixed (see Fixes). Remaining limits, recorded in 14 "Changes":
  - `SqliteConnection` is not thread-safe, so concurrent Stage calls on one caller transaction are not supported.
  - A deferred caller transaction can get `SQLITE_BUSY` on its first write. That error propagates unchanged, and the retry is the caller's.
  - The relay already uses `BEGIN IMMEDIATE`.
- The delivered-row and mapping cleanup jobs are specified but not shipped (14 §10.1).
- A stopped `OutboxRelay` cannot be restarted. The host must be recreated.
