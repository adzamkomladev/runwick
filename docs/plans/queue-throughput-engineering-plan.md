# Runwick queue performance engineering plan

24 November 2026 · baseline v0.1.5 (`de189dc`) · checked against main `110b967`

**First release objective:** make short, durable jobs cheap to accept and settle. Measure shared dispatch and worker coordination first, then use those results to prioritize PostgreSQL’s payload lookup, Redis’s plain producer path and SQLite’s single-writer transaction body. Give each change a separate result for single dispatch, bulk dispatch, and drain. A worker improvement cannot raise producer-only throughput. A producer improvement can raise mixed throughput while leaving preseeded drain unchanged.

**Evidence status.** The November CI run and follow-up investigation supply the measurements below. The prototypes, thresholds and sequence in this document are proposals. The Redis tuned result and PostgreSQL statistics experiment are specific to their reported workloads. There are no new benchmark measurements in this plan. Stages 1 and 2 establish the evidence for implementation. After Stage 2, producer and worker changes can proceed independently. Run comparative timings sequentially on the reference machine. Stage 5 is conditional.

## Stage 2 — Isolate the shared engine

The Redis worker settings alone moved the same binary from 540 to 1,616 and from 407 to 959 jobs/s in two disk-backed backlog comparisons. That establishes that scheduling affects drain. It does not quantify the CPU overhead of the shared worker. Producer-only workloads run without consumers and exercise a different shared path. Investigate both before attributing a cross-store gap to the engine. [Measured comparisons](../reports/queue-benchmark-2026-11-24-investigation.md)

### A shared .NET experiment for all three producers

Measure the public dispatch entry point, dispatch of a freshly prepared command, and store call independently. Time registry lookup, user job serialization, validation/canonicalization, fingerprints, queue wait, encoding the driver request, server execution, commit and receipt decoding. Use paired, tracing-off release runs for throughput, separate EventPipe CPU/allocation traces for attribution, plus native/store counters. Bound caches by registered job/serializer/policy shape. Never cache per-request identity, caller metadata or mutable user objects. [Dispatch preparation](../../src/Runwick/Dispatch/DispatchPreparer.cs) · [Fingerprint implementation](../../src/Runwick/Serialization/Fingerprints.cs) · [EventPipe tooling](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/dotnet-trace)

For each provider, compare ordinary public dispatch with dispatch of a command prepared outside the timed store call. Use fresh operation and job IDs for every submission, identical payloads and effective options, and a separate preparation timer. Report preparation plus submission alongside submission alone. Exercise both fresh single jobs and fresh batches. Time replay of an existing receipt separately.

### Worker coordination with a real store

For each provider, seed identical, verified ready backlogs in isolated stores. Run the public worker and a minimal benchmark driver through the same provider claim and finish methods. Give both the same no-op handler, worker slots, payloads, leases, tokens, receipt semantics, finish usage metadata and terminal-state checks. In the first pair, match the observed claim and finish batch sizes, outstanding call limits and connection budget. Record the actual distributions in both arms. Keep a separate startup clock and time the drain through confirmed settlement. Treat the direct driver as a diagnostic control for the plain healthy path.

In the second pair change only claim/refill or finish-flush timing, one at a time, with the same slot budget and durability. Sample how long runnable backlog and idle handler slots coexist. Correlate those intervals with available tickets, claim requests awaiting replies, handler-return-to-confirm p99, finish buffer depth, batch sizes, managed CPU and store CPU. Start at 16 fixed slots in one eligible lane, repeat at 64, then check whether the finding survives multiple lanes. The pool's claim overlap rules and the completion coordinator are the first trace points. [Pool coordinator](../../src/Runwick/Worker/PoolCoordinator.cs) · [Completion coordinator](../../src/Runwick/Worker/CompletionCoordinator.cs)

| Observation across matched pairs | Next action |
|---|---|
| Prepared submission is fast, while preparation consumes a material share of the single or bulk budget | Profile shared serialization and fingerprint construction in Stage 3. |
| Direct drain is consistently faster at matched batch sizes and in-flight limits | Trace ticket acquisition, lane selection, invocation and completion handoffs. Introduce one targeted change behind the normal worker entry point in Stage 4 and rerun the original pair. |
| Throughput separates only when refill or flush timing changes | Test a scheduling-policy change in Stage 4. Check pickup, lease margin and fairness with competing workers. |
| Both worker arms plateau together and store counters identify expensive operations | Prioritize the corresponding provider work in Stage 4. |
| Batch distributions differ unintentionally, or the gap varies with run order | Tighten the control and repeat before choosing a rewrite. |

**Exit evidence.** Record the paired rates, gap and counters for single acceptance, bulk acceptance and drain by store. Identify the first attributable cost and the experiment that would falsify the diagnosis.

## Stage 3 — Improve job acceptance

### Shared producer optimization

The code already reuses the payload's canonical value, caches repeated policy encodings within a batch, and streams the batch command digest. If preparation limits throughput, compare stock with a direct canonical writer for stable envelope fields and a pre-encoded immutable registered default policy. Keep exact bytes and domain-separated digests. Compare custom converters, Unicode, numeric equivalence, reordered keys, imports, old receipts, and export-after-lost-reply against the existing implementation. Evaluate source-generated user serialization only for profiles that support it. If preparation accounts for 10% of total service time, eliminating it entirely can yield at most ~1.11× on a serial path. Prioritize the store when that is the measured bound. [Serialization specification](../spec/02-serialization-and-wire.md) · [System.Text.Json modes and fallback](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/source-generation-modes)

### Redis producer

The original disk-backed, AOF-always CI medians give distinct targets. At one caller Runwick accepted 1,084/s and Wolverine 2,807/s. At 16 callers the figures were 3,063 and 18,805/s. Achieving 90% of those historical rates requires about **2.33× and 5.53×** respectively. For bulk it requires **2.03×** against BullMQ .NET (6,612 vs 14,897/s). Wolverine has no measured native bulk API. At 16 and 64 workers the corresponding Wolverine drain targets are about 7,169 and 8,750/s, compared with Runwick's 2,864 and 4,296/s. Use fresh paired ratios for qualification. Wolverine's immediate send serializes an envelope and awaits one XADD. It provides a useful measurement of the device and transport budget for basic admission. Runwick also makes an orderable job, exact replay decision, event and management indexes visible at acceptance. [CI tables](../reports/queue-benchmark-2026-11-23.md) · [Wolverine inline sender at tested revision](https://github.com/JasperFx/wolverine/blob/1a8fde0675c9e334aea64fd8d83de3968b700ee7/src/Transports/Redis/Wolverine.Redis/Internal/InlineRedisStreamSender.cs)

#### Establish a strict admission budget

On one Redis 8.2 instance per arm, run public single dispatch at 1 and 16 callers and bulk with 1 caller at 8, 32, 64 and 100 jobs/call. Run both BullMQ harnesses at the same chunk size and in their native 1,000-item arm. The .NET comparison harness needs a batch parameter. Use unique 1 KiB payloads, a fresh fixture and a retained fixture, no worker during admission. Collect separately client preparation/fingerprint, metadata serialization, provider wait, script service, recovery calls, AOF growth, actual physical fsyncs if observable, managed allocations, reply bytes and confirmed-add p50/p95/p99. Use separate tracing and timing runs. Add a pre-prepared request through the real provider and a raw RESP replay of prepared requests with fresh IDs and unchanged argument shapes to locate CPU versus RTT versus fsync. Compare against fresh single XADD with equivalent wire bytes as a diagnostic. At 16,924/s (90% of Wolverine's historical 16-caller rate) a serial primary has about **59 µs/job** of main-thread capacity. If measured service alone exceeds that, network tuning alone cannot close the gap. Redis can synchronize multiple concurrent writes in one fsync with AOF always. #### Specialize a fresh plain Dispatch on the existing layout

Time two independent changes. First replace the per-item nested JsonObject construction in DispatchCallAsync for eligible calls with a typed writer over the existing wire shape, validating the same payload/policy and preserving the supplied command fingerprint. Second introduce a narrow producer script descriptor for a fresh layout-2, ordinary ready job with no keys, scopes, rates, schedule or management actor. Reuse the authoritative gate, deadline, receipt and recovery rules. Predict every required after-image before the first write, including job, payload, four ready/listing indexes, type count under its existing backfill rule, receipt and expiry, dispatched event, revision and wake. Use absolute values for replay-safe recovery. An ineligible or ambiguous shape hands the original operation to the generic script before mutation. A lost reply replays the same historical result. Compare the wire-only and script-only arms, then combine winners. The generic implementation already avoids writing a whole guard for a successful inline operation. The proposed saving is the generic decision overlay, allocations and duplicate encoding. #### Extend the same transition to homogeneous DispatchMany

One public DispatchMany command has one receipt and an ordered item vector. Concurrent callers grouped by DispatchGroup retain individual identities and receipts. Keep those contracts distinct. For the public batch perform one queue-registration check per distinct queue, verify distinct generated job IDs locally inside the script, then use a bounded multi-key EXISTS in the application's hash slot. A nonzero count, mixed policy shape, duplicate, key conflict, exceeded inline byte/key/operation/argument limit or an unqualified topology takes the existing path before mutation. Precompute eligible jobs and write aggregated absolute type counts once per type, preserving backfill semantics, per-job payloads, ready and listing entries, event IDs and input ordinal ordering. The current generic writer already coalesces updates to the same key. Test the value of avoiding its per-item staged dictionaries, repeated queue lookups, sorting for scope seeding and full admission passes. Keep the existing supported 100-item envelope and original recovery continuation for larger projections. Count guard writes, extra recover round trips and renew p99 under concurrent bulk traffic before proposing any limit change. Existing opt-in grouping with two sends in flight reached **0.81×** ungrouped at 16 callers and had worse p99 on the older shared host. Retest bounded pipelining only after per-item service falls, holding offered concurrency fixed. ### PostgreSQL producer

**Start with payload validation on bulk acceptance and slot saturation on single acceptance. Budget a separate investigation for drain.** At release, 16 callers accepted 518 jobs/s and single-caller bulk accepted 1,106/s. At 16 and 64 slots 728 and 1,321 jobs/s finished. The historical 90% targets against River are approximately 5,141 single adds/s, 31,469 bulk adds/s, 5,063 and 13,654 finishes/s. Against pg-boss they are 4,107, 41,484, 5,659 and 8,690 respectively. Treat these as sizing figures until both systems run on one host with matching clocks. At 500 offers/s the published 365 finishes/s includes catch-up after offering stopped. Only 5,280–5,675 of about 15,000 had finished during the window. Report both clocks. [Release comparison](../reports/queue-benchmark-2026-11-23.md) · [Current investigation](../reports/queue-benchmark-2026-11-24-investigation.md)

**What upstream actually executes.** River 0.50 selects due rows by queue/priority/time/ID with a bounded ordered lock, updates the job to running and returns it. Its ordinary bulk insert unnests typed arrays into one job relation with duplicate handling and a returned row. Completion updates a set of running rows. pg-boss 12.38 loads bulk input with `json_to_recordset`, fetches with ordered `SKIP LOCKED` and uses a set update for completion. Its SQL includes an attempt fence using job ID and retry count when requested. In CI River used a 1 ms fetch cooldown and `InsertMany` for timed adds. Its `InsertManyFast` COPY path seeded drains outside the clock. pg-boss used a single batch callback, burst fetch and a durable database-state check. Runwick already has set-oriented creation and an ordered locked claim, but also writes attempts, generations, lifecycle events and durable command outcomes. Record database work per job and compare identical producer batch sizes separately from each native configuration. #### Bound bulk validation cost on the first load

Migration 0028 replaced the composite profile foreign key with a job PK foreign key and two profile checks. A statement trigger joins the newly written payloads to jobs. On a 1k seeded database one nested plan scanned 2,950 unrelated rows per lookup. For 10k ensuing jobs at batch 100, one caller, the two controls had 1.42M buffer hits and 488–733 adds/s. An out-of-band `ANALYZE runwick.jobs` arm had 30k hits and 1,445–1,460/s. A three-pair correlated lateral lookup still exceeded a million hits. Build a plan fixture that compares the unchanged cold control, analyzed control, and a declarative composite-FK reference arm.

For the latter restore the profile unique key and FK in a disposable schema, remove the replaced checks and retain 0028's other index changes. This quantifies the exact trade of bounded validation for an extra index write on each hot job version. If both approaches cost too much, prototype one authoritative profile row per immutable job identity and reference it from payload storage, accounting for identity and retention writes.

Run 0, 1k and 200k retained jobs, several applications, 1/100/1,000 items and interrupted first imports. Use sampled nested plans, actual rows removed, shared hits per accepted job, WAL/job, and drain p99.

Proposed gate at batch 100: ≤10 hits per accepted job for the validation query in cold and retained fixtures, no application-wide filtered scan growing with history, ≥20% paired cold bulk improvement, and ≤10% regressions in warm bulk and drain. Preserve missing-parent and profile-mismatch errors, simultaneous same-statement profile changes, staged rollback and cross-session integrity. An operator-run early statistics refresh is a measurable mitigation when permissions allow it. Count maintenance time and cold behavior when evaluating any automatic first-load trigger. #### Exercise existing single-call grouping before changing the dispatcher

### SQLite producer

The CI medians were 610 and 1,344 single adds/s at 1 and 16 callers, 3,016 bulk jobs/s at 100 items/call, and 826 and 935 finishes/s at 16 and 64 slots. #### Single adds, isolate the commit floor and remove repeated SQL inside the writer

At one caller, 4,071/s allows 246 µs for the entire durable call. Measure a one-row insert + FULL commit on the same file profile and the cost of a full Runwick call, splitting client preparation, queue wait, lock acquisition, SQL body, commit/checkpoint and reply. If the minimum-path mean already exceeds that budget, publish the same-host sustainable bound. No-wait grouping only helps when callers overlap. Keep the proven eight-command/1 MiB cap and priority order. Start with parameter/statement reuse for stable shapes and one decided receipt insert for a new plain dispatch, using the existing indexed cross-class replay check and deadline checks under BEGIN IMMEDIATE. SQLite FinishMany provides the precedent. If repeated setup still dominates at 16 callers, specialize a group of already-admitted plain dispatches. Read the gates once under the file writer lock for that store/application, fetch existing command IDs as a set, and bulk-write fresh rows plus *independent* receipts. Preserve per-command decision times, payload byte bounds and wake-after-commit. Reject duplicate command/proposed-job IDs, keyed/scoped items, cancellation races or unusual outcomes from fast-path eligibility and run them through the existing savepoint logic. Roll back and resolve any unknown shared commit by original command ID. Keep staging on the caller’s transaction. Test replay + conflict + expiry mixed with fresh siblings, one failing member, whole-commit failure and no reply before commit. Benchmark 1/2/8/16/32 callers with independent receipts, including steady mixed writes and lease renewals. #### Bulk adds, reduce preparation cost at the current public cap

Solid Queue 1.2.1 inserts jobs together, then inserts ready executions together for unconstrained jobs and handles constrained jobs individually. Runwick already uses multi-row writes for jobs, payloads, generations and dispatch events. Its InsertRows builds fresh SQL, parameter names, parameter objects and row arrays for each statement and disposes the command. ### When incremental improvements are too small

Before a new queue engine, build a small **strict lifecycle prototype** with the same 1 KiB payload, receipt resolution, lease fence and durable terminal boundary. Compare four arms on the same hardware: (1) minimal durable backend operation as a diagnostic ceiling, (2) plain admission plus exact retry and immediate claimability, (3) the same plus fenced settlement and mandatory history/index visibility, and (4) the full public Runwick path. If arm 3 beats production by several-fold, port that representation behind the existing eligibility checks. If arm 3 remains far from the target, publish which guarantee or hardware limit consumes the budget before committing to a new schema.

One concrete layout to test for ordinary SQL jobs is a narrow mutable execution row keyed by application and job ID, an immutable payload/policy record, and append-only attempt/event facts. Size competing designs by what they write and must read: add the mandatory event/receipt/index writes to the prototype immediately, then run claim, cancel, retry, inspect and cleanup through it.
