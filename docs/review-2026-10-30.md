# Architecture review of the Runwick planning baseline

Reviewed 2026-10-30 against every document under `docs/`. This is the G-0 review input the [backlog](implementation-backlog.md) asks for (SP-001). It records what was verified, what was corrected in place, what still needs your decision, and what to watch when code starts.

## 1. Verdict

**The plan is sound and implementable. Recommended G-0 disposition: approved with feature gates**, once the five decisions in §4 are made.

What was checked:

- Every design document was read end to end and cross-checked for internal contradictions (lock orders, state names, budgets, defaults, lifetimes, lock ranks across the storage, worker, capacity, scheduler, outbox and consolidated-schema documents).
- External facts the plan leans on were verified today: Cronos really does use AND for restricted day fields (the OR adapter is justified); StackExchange.Redis 3.4.20 is the current stable (released 2026-10-23); `Inertia.Net` 1.5.3 exists; the .NET 10 System.Text.Json strictness controls, `HostOptions.ShutdownTimeout` 30 s default, `CancellationTokenSource.CancelAsync`, `TimeProvider.GetElapsedTime`, `WAITAOF` semantics and PostgreSQL `FOR NO KEY UPDATE … SKIP LOCKED`, `clock_timestamp()` vs `now()`, and `CREATE INDEX CONCURRENTLY` restrictions are all described correctly.
- The arithmetic in the timing, capacity and scheduler packets was re-done by hand (lease/renewal inequalities, the 15→16 hysteresis trap, the 1:3 and 6:3:1 shares, the renewal-wave example). All consistent, with one exception corrected below.

What is genuinely strong and should not be reopened:

- Ownership model: random ownership token + storage-side fresh time after lock waits + "stale owner can observe but never mutate". This is the heart of the library and it is right.
- Begin as the accounting point, with a separate pre-start abandonment guard. The seven states earn their keep.
- Command receipts for ambiguous commits, with `Replayed`/`Effect` split and the explicit rule that NotObserved ≠ rolled back.
- Reservation + all distributed permits in one transaction; permits validated by expiry so crashes self-heal.
- Dispatch/Stage never locking an existing job (removes the obvious deadlock with Finish/retry).
- "Local ticket before durable reservation" and "ticket held until retirement" — this is what keeps memory bounded during a storage outage.
- The honesty rules: no exactly-once claim, no "cancellation stopped the code" claim, no fabricated zero when telemetry is stale.

## 2. Corrections applied in place

| Where | What was wrong | Fix |
|---|---|---|
| [capacity-defaults-and-budgets.md §5](architecture/capacity-defaults-and-budgets.md#5-pressure-and-uncertainty-gates) | Admission pressure gates used absolute constants (stop when margin <25 s, resume when ≥30 s). They only hold for the 60 s/10 s defaults; with a 30 s lease the maximum possible confirmed margin is 20 s, so a worker would pause admission and **never resume**. | Gates are now derived: `StopMargin = (lease − safety) − renewalMax − requestTimeout − schedulerAllowance`, `ResumeMargin = StopMargin + requestTimeout`. Reproduces 25 s/30 s for the defaults; startup rejects `StopMargin ≤ 0`. |
| [capacity-defaults-and-budgets.md §1](architecture/capacity-defaults-and-budgets.md#1-capacity-ownership-and-default-mode) | "Hard maximum 4 unless explicitly raised" implied a separate maximum setting for fixed pools, contradicting `FixedConcurrency(8)` in the API example. | Clarified: `FixedConcurrency(n)` sets target and maximum to `n`. |

## 3. Recommendations recorded in the design documents (need your sign-off)

These are marked "Review recommendation 2026-10-30" inside the affected documents so an implementer sees them in context. None silently rewrites a contract.

### R1 — Renew without a replayable receipt (write amplification)

[storage-command-protocol.md §4](architecture/storage-command-protocol.md#4-lost-responses-and-replay), [execution-defaults-and-timing.md §2](architecture/execution-defaults-and-timing.md#2-proposed-initial-values).

Renew runs every ~15 s for every running attempt. With receipts, a 16-slot worker writes ~1 receipt row/s just for heartbeats, and every one of them is retained 10 minutes and then deleted — that is the single largest write stream in the system after the job rows themselves. A lost Renew reply is already safe without a receipt: the worker just sends another ownership-checked Renew. Recommend: Renew is validated and atomic but **not** replayable. Reserve/Begin/Finish/Recover keep receipts.

### R2 — Add `ReleaseReservation` to SP-008

[implementation-backlog.md SP-008](implementation-backlog.md#3-foundation-and-first-postgresql-milestone), [worker-engine-internals.md §9](architecture/worker-engine-internals.md#9-shutdown-and-cancellation-resistant-handlers).

Without it, every graceful shutdown leaves reserved-not-begun jobs stuck for a full lease (60 s) and increments their abandonment guard for something that is not a crash. It is a ~10-line transaction using the existing Finish lock order. Cheap now, awkward to retrofit.

### R3 — Split the fixed-window fingerprint into business + policy digests

[dispatch-wire-contract.md §3](architecture/dispatch-wire-contract.md#3-fixed-window-request-fingerprint-v1).

As specified, changing a library or application *default* (say, the initial retry delay in a Runwick patch release) makes every in-window idempotent re-dispatch return a conflict. Users will experience this as "we upgraded Runwick and our checkout retries started failing." Recommend comparing only business intent for reuse and surfacing policy drift as a receipt diagnostic.

### R4 — Expose the autoscaler's "cannot reach the maximum" behavior as a rule, not a footnote

[capacity-defaults-and-budgets.md §7](architecture/capacity-defaults-and-budgets.md#7-acceptance-workloads-and-evidence) already shows target 15 never reaching max 16 because the 20 % hysteresis band needs 18. Two cheap options: (a) when `candidate == MaxConcurrency`, allow the final step regardless of band; (b) apply the band to the unclamped estimate. Either is fine; pick one in SP-014 and add it to CAP-07. Left as-is it will generate "why does auto 1–16 stop at 15?" issues forever.

### R5 — Decide the dashboard transport before SP-023, not after

[dashboard-integration-closure.md](architecture/dashboard-integration-closure.md). `Inertia.Net` 1.5.3 has roughly 1.2 K lifetime downloads. That is a one-maintainer dependency on the critical path of an embedded admin UI. For a dashboard whose routes are all owned by the library, Inertia buys little: a prebuilt React SPA served from embedded assets plus the already-planned authorized JSON endpoints gives the same product with no server adapter at all, cleaner host isolation (no global MVC filters), and one fewer compatibility axis. The handoff chose Inertia.NET, so this is your call; the spike (SP-023) should explicitly compare the two rather than only validate Inertia.

### R6 — Transactional completion (exactly-once for same-database effects)

[public-api-contract.md §6](architecture/public-api-contract.md#6-caller-owned-transactions-remain-staged), [runwick-explained.md §9a](runwick-explained.md#9a-can-we-have-exactly-once).

The plan lets a caller *enqueue* inside its own PostgreSQL/SQLite transaction (`StageAsync`) but has no mirror for *completing* inside one. Adding `IPostgresJobCompletion.CompleteInTransactionAsync(NpgsqlTransaction, ct)` (and the SQLite twin), callable from inside a handler, gives genuine exactly-once for side effects that live in the same database as Runwick's tables — the common case for a monolith-first library — and, combined with a caller-side "calls already made" table plus provider idempotency keys, effectively-once for external calls.

Fit with the existing design: the operation is Finish/1 executed on the caller's connection with the same ownership checks and the same lock order (store gate → app gate → receipt → job → active key → scopes), taken *after* the handler's business locks. Runwick never commits, rolls back or retries the caller's transaction. Engine consequences to specify: (a) the attempt runner treats a successful handler return as "outcome already staged" and must observe the caller's commit outcome — if the handler returns without the transaction having committed, that is a pipeline fault, not a success; (b) if the commit reply is lost, the existing unknown-Finish receipt resolution applies unchanged; (c) lease renewal continues normally during the handler as today, so a long business transaction does not need a longer lease; (d) the caller's transaction must be on the same store (reuse `StageAsync`'s store-identity validation). The staged-completion token should be an explicit object returned from `CompleteInTransactionAsync` that the handler returns or that the engine detects, so a handler cannot accidentally stage and then also be finalized by the normal path.

Suggested placement: after SP-010, alongside SP-011 (it reuses Finish and the staging validation from SP-006). It is the single most valuable "exactly-once" story the library can truthfully tell; the honest public sentence becomes "at-least-once everywhere; exactly-once for same-database effects via transactional completion; idempotency keys for the rest."

### R7 — Hosted store ("Shape C") decided; seams and backlog additions

[commercial-strategy-and-seams.md](commercial-strategy-and-seams.md). The user selected a hosted job store (Hatchet-style) billed per run (first Begin of a generation; failure retries free), concurrency slots and retention, with a free CLI. The engine is unchanged: `Runwick.Cloud` is a client driver over gRPC and the server is core + the PostgreSQL driver + tenancy/metering. Added SP-031–034 to the backlog; v1 seams: versioned event export (SP-011/022), transport-free `IManagementSession` (SP-020), public versioned management API (SP-032), frozen telemetry names plus `Runwick.OpenTelemetry`, log table and Grafana assets (SP-022). First PostgreSQL milestone unchanged.

## 5. Design observations to carry into implementation (no document change needed)

**Performance shape, not correctness.**

- *Two round trips per job.* Reserve and Begin are separate transactions by design. The P-01 target (100 finishes/s on one worker) and especially P-02 (store saturation) will be bounded by this plus the "one claim in flight per pool, prefetch 0" rule before the database is. The protocol already permits a batched Reserve and a combined operation version later; measure first (SP-010), but expect to need batch Reserve for P-02. A `ReserveAndBegin/1` variant for the common no-rate-scope path would also make rate deferral simpler (no attempt to close, no permits to release) — worth a spike, not a baseline change.
- *Receipt table growth.* Finish receipts retained 24 h at 100 jobs/s is ~8.6 M rows live. Partition `storage_commands` by retention class (or use one table per class) so cleanup is `DROP PARTITION`/`TRUNCATE`, not row deletes under the receipt lock. Same for `queue_events`.
- *Job IDs.* Random UUIDv4 primary keys scatter B-tree inserts. Use `Guid.CreateVersion7()` for job/attempt IDs (time-ordered, still unique) and keep ownership tokens random. Cursor order is `(eligible_at, job_id)`, so this changes nothing semantically. Remember the plan's own warning about canonical UUID byte order vs CLR `Guid` layout.
- *Receipt insert shape.* "Insert/lock its command row" must be `INSERT … ON CONFLICT DO NOTHING` followed by `SELECT … FOR UPDATE` (a plain duplicate insert aborts the whole PostgreSQL transaction). `ON CONFLICT` correctly waits for an in-progress conflicting transaction, which is exactly the serialization the protocol wants.

**API ergonomics gaps (non-breaking to add later, cheaper to add now).**

- ~~No batch dispatch.~~ **Added 2026-10-30:** `DispatchManyAsync` / `PrepareMany` / `StageManyAsync` in the API contract §5 (atomic batch, per-ordinal receipt, `ContinueOnConflict`, 100-item / 2 MiB bound, materialization lock order) and in SP-006.
- No handler-side progress or "extend my own deadline" hook on `IJobContext`. Deliberately excluded (good: renewal is engine-owned), but write that reason in the public docs or users will ask.
- `[Queue]` and `[Priority]` are short generic attribute names; Hangfire ships a `QueueAttribute`, so a migrating app referencing both packages gets CS0104. Consider `[JobQueue]`/`[JobPriority]`, or keep the short names and document the alias.

**Operational.**

- The 25 s shutdown budget assumes Runwick gets most of the host's 30 s. Hosted services stop sequentially; a host with several services before Runwick will cut this. Document "put `AddRunwick` last among worker-ish services" or register the worker hosted service first so it stops last.
- Kubernetes `terminationGracePeriodSeconds` defaults to 30 s and the SIGTERM arrives before the host token — same budget, worth a sample manifest.
- The capability-filtered ready query (`EXISTS … unnest(...)`) is a post-filter over the ready index; a queue whose head is a version no worker supports pays that scan on every poll by every replica. The plan already flags it; make the "no capable worker" dashboard signal part of SP-012, not a later nicety.

**Documentation.**

- The planning corpus is thorough but repetitive and heavy with provenance disclaimers. Before SP-002, extract one normative spec per subsystem (protocol, PostgreSQL, worker, scheduler, API) with the disclaimers removed and the review notes resolved. The current set stays as design history. Implementers should not need to reconcile six documents to learn one lock order.
- A beginner-facing explanation of the whole library now exists at [runwick-explained.md](runwick-explained.md).

## 6. Smaller notes

- Default retry delays differ between the historical [uniqueness-and-execution.md](uniqueness-and-execution.md) (10 s / 5 min) and the current timing packet (5 s / 60 s). The historical document is correctly marked superseded; nothing to change.
- `job_attempts.outcome` lists `admission_deferred`; the review recommends adding `released` for R2.
- `runwick.lease.margin` is a good metric; also emit a counter for pressure-gate activations by reason so CAP-10 is observable in production.
- `[UseJobMiddleware("tenancy", Order = 100)]` alias resolution: unknown alias fails *worker* validation; make the error message name the job and the alias, and say which `AddMiddleware<T>("alias")` call is missing.
- The scheduler's "run-once" job carries both its scheduled instant and covered range. Expose both on `IJobContext` schedule metadata so a report job can say "covering 02:00–09:10".
- NuGet package-name availability for `Runwick` is still unchecked; the name is used by unrelated projects in other ecosystems (Go, Rust, npm). Check before SP-002 so namespaces do not need renaming later.
