The Redis store keeps Runwick's data on one Redis primary that writes every change to its append-only file and syncs it to disk before it replies. Producers and workers can run on many hosts. Job behaviour is the same as on PostgreSQL: the same states, retries, receipts, uniqueness and rate rules.

Redis is only safe for jobs with the right server settings, so Runwick checks them before it starts and keeps checking while it runs.

## Requirements

| Item | Requirement |
|---|---|
| Server | Redis 8.2 or newer |
| Topology | One standalone primary. Optional: a Sentinel-managed primary, or a Redis Cluster in which each application lives on one node, both with strict write authority (see below). |
| Persistence | AOF with `appendfsync always` (see below) |
| Package | `Runwick.Redis` (uses StackExchange.Redis) |

## Server configuration

Start Redis with these settings. Runwick refuses to run with anything else:

```conf
# redis.conf
appendonly yes
appendfsync always
no-appendfsync-on-rewrite no
maxmemory-policy noeviction
aof-load-truncated no
```

| Setting | Why |
|---|---|
| `appendonly yes`, `appendfsync always` | Every write is on disk before Redis replies, so a confirmed job survives a crash. |
| `no-appendfsync-on-rewrite no` | Keeps fsync on while the AOF is being rewritten. |
| `maxmemory-policy noeviction` | Redis must never drop keys to free memory. A full server returns errors instead. |
| `aof-load-truncated no` | A damaged AOF stops Redis at startup instead of quietly loading less data. |

### Faster, less durable: `appendfsync everysec` (opt-in)

If you can accept losing about the last second of confirmed writes after a machine crash, run Redis with `appendfsync everysec` and tell Runwick:

```csharp
builder.UseRedis(configuration, o => o.Persistence = RedisPersistence.AofEverySecond);
```

Use `RunwickRedisMigrations.MigrateAsync(configuration, RedisPersistence.AofEverySecond)` to install. Runwick checks the setting the same way: a server on `always` is refused under this option, and the default option refuses a server on `everysec`. Everything else in the table above still applies.

| | `always` (default) | `everysec` (opt-in) |
|---|---|---|
| Redis process is killed | no confirmed write is lost | no confirmed write is lost |
| Machine or operating system crashes | no confirmed write is lost | about the last second of confirmed writes can be lost |
| Failover to a replica | only with the Sentinel or Cluster option below | not supported |
| Receipt's `ConfirmedAcknowledgementProfile` | `redis.aof-always-single-primary-v1` | `redis.aof-everysec-single-primary-v1` |

In our drain test (20,000 jobs, 16 workers, one shared host) `everysec` drained about 1.5 times faster and inserted about 1.16 times faster, in every one of five pairs. A second test on 2026-11-23 found about 1.8 to 1.9 times faster drains; the bytes Redis writes per job do not change, only how often they are flushed to disk. A lost write after a crash looks like a dispatch that was confirmed but is not there, so use this only for work you can resend or regenerate.

Size `maxmemory` with room to spare. With `noeviction`, a full server refuses writes, and dispatches fail until you free space.

<Callout type="warning" title="Keep CONFIG GET readable">

Runwick reads the settings with `CONFIG GET` and `MODULE LIST`. If an ACL blocks either, the value counts as unverifiable and the store refuses to run. Restrict `CONFIG SET` with ACLs if you need to, but leave `CONFIG GET` and `MODULE LIST` allowed for Runwick's user. Do not remove `CONFIG` with `rename-command`. Managed Redis services that hide `CONFIG` are not supported. If you name a user (`user=` in the connection string), Runwick also checks with `ACL WHOAMI` that it is connected as that user and refuses with `primary_authentication_failed` otherwise: the Redis client otherwise falls back to the `default` user when the password is wrong and `default` is open. Leave `ACL WHOAMI` allowed too.

</Callout>

## Install and migrate

```bash
dotnet add package Runwick
dotnet add package Runwick.Redis
```

Write the store's identity once before the first start:

<Tabs>
  <Tab label="C#">

```csharp
using Runwick;

await RunwickRedisMigrations.MigrateAsync("redis-primary:6379,password=...");
```

  </Tab>
  <Tab label="CLI">

```bash
export RUNWICK_REDIS="redis-primary:6379,password=..."
runwick migrate --provider redis --connection-env RUNWICK_REDIS
```

  </Tab>
</Tabs>

Running it again does nothing if the store is already installed. Without it, the app refuses to start because the store is not installed.

## Register the store

```csharp
builder.Services.AddRunwick(runwick =>
{
    runwick.Application("notifications")
        .UseRedis(builder.Configuration.GetConnectionString("Redis")!, o =>
        {
            o.ProfileRecheckInterval = TimeSpan.FromSeconds(30);
        })
        .AddJobsFromAssemblyContaining<SendPush>();
    runwick.AddHandler<SendPush, SendPushHandler>();
    runwick.AddWorker(w => w.Pool("main", p => p.Queues("default").FixedConcurrency(4)));
});
```

The configuration string is a StackExchange.Redis string. Runwick uses only the endpoint, credentials, TLS settings, `defaultDatabase` and `connectTimeout` from it, and never logs it. Several endpoints, or a Sentinel service name, are refused at startup with `topology_unsupported` unless you turn on the Sentinel or Cluster option below.

| Option | Default | Allowed | What it does |
|---|---|---|---|
| `ProfileRecheckInterval` | 30 s | 5 s to 5 min | How often the settings and topology check runs while the app runs. |
| `Sentinel` | none | none or settings | Follow a Sentinel-managed primary with strict write authority. See below. |
| `Cluster` | none | none or settings | Run on a Redis Cluster, writing only to the node that owns the application's slot. See below. |
| `GroupDispatches` | off | on or off | Sends plain dispatches that arrive while another send is in flight together, in one Redis call. See below. |
| `UseFunctions` | off | on or off | Runs the worker commands from a Redis function library (`FCALL`) instead of scripts (`EVALSHA`). Off by default because it measured slower. See [What Runwick checks](#what-runwick-checks). |
| `MaxGroupItems` | 8 | 2 to 16 | Most dispatches in one grouped call. |
| `MaxGroupBytes` | 128 KiB | 16 to 128 KiB | Most request bytes in one grouped call. A larger dispatch goes alone. |
| `MaxGroupsInFlight` | 2 | 1 to 16 | Sends per application that may be in flight at once. |

### Grouped dispatch (opt-in)

With `GroupDispatches` on, a dispatch that finds a free send slot goes out alone, at once, exactly as before. A dispatch that arrives while every slot is busy waits for the next free slot and goes out with the others that are waiting, in one Redis call. A caller never waits for company that is not already there, and nothing waits on a timer.

Every dispatch in a group still has its own command ID, receipt and event. Resending one later, alone or in another group, returns its original job. If the reply to a group is lost, each caller gets the usual "outcome unknown" for its own dispatch and resolves it as before. Dispatches with uniqueness keys, concurrency scopes or rate scopes always go alone. Delayed dispatches can be grouped. Cancelling a call that is still waiting leaves nothing behind. Cancelling after the group was sent cannot undo it, and the caller gets the real result.

Grouping only helps when many callers dispatch at the same time. It needs `ProducerOptions.MaxConcurrentCalls` above 1 to have anything to group.

## Sentinel: a primary with replicas (opt-in)

Runwick can follow a primary that Redis Sentinel manages. The aim is simple: **Runwick only writes to a primary it has just checked, and stops writing the moment it cannot tell.** It does not try to keep working through a failover at any cost.

```csharp
builder.UseRedis(
    "sentinel1:26379,sentinel2:26379,sentinel3:26379,serviceName=mymaster,password=data-password,sentinelPassword=sentinel-password",
    o => o.Sentinel = new RedisSentinelOptions());
```

List your Sentinels and the service name, not the data servers. Use `user` and `password` for the data servers and `sentinelUser` and `sentinelPassword` for the Sentinels (the TLS setting applies to both). Every data server must run the same settings as above, `appendfsync always` included; `everysec` cannot be combined with Sentinel. Run the migrator with the same string and options; it finds the primary through the Sentinels and checks it the same way before it writes anything:

```csharp
await RunwickRedisMigrations.MigrateAsync(sentinelString, new RedisOptions { Sentinel = new RedisSentinelOptions() });
```

From the command line: `runwick migrate --provider redis --redis-topology sentinel --connection-env RUNWICK_REDIS`. The `store` commands and `doctor` take the same flag. If the data servers refuse the password, the error says `primary_authentication_failed` (or `primary_permission_denied` for a missing ACL permission) rather than "unreachable".

| Option | Default | Allowed | What it does |
|---|---|---|---|
| `AuthorityRecheckInterval` | 1 s | 250 ms to 10 s | How often the primary is checked again. |
| `AuthorityTtl` | 4 s | 1 s to 30 s, at least twice the recheck interval | How long one successful check lets commands go out. |

**What Runwick checks each time.** A majority of your Sentinels must name the same primary and report it healthy. That primary must pass the settings check above. If it is a different server from the one Runwick used before (a failover), it must also continue the same history: the Sentinel promoted a replica that had everything Runwick saw at its last check. And the store's identity and revisions must not have gone backwards.

**What happens when something is wrong:**

| Situation | What Runwick does |
|---|---|
| A Sentinel majority is unreachable (you cannot reach them, they disagree) | Keeps writing until the 4 s lease runs out, then stops sending anything. Starts again as soon as a check passes. |
| A Sentinel reports the primary down, or a failover has started; the connection to the primary breaks | Stops sending anything at once and checks again. |
| A failover finished and the new primary continues the old history | Moves to the new primary and resumes. Jobs and receipts written before are intact. |
| The new primary does not cover the history Runwick last saw (a replica that was behind), or the store identity or revision went backwards | **Blocked.** Every call fails as incompatible until you reconcile the histories and restart the process. |

Calls that are stopped are never sent, so they have no effect. A call that was already in flight when the primary failed has the usual "outcome unknown"; resend it with the same command and it is answered from its receipt, if the receipt survived the failover. The Store page shows the state, the primary, how many Sentinels agree, and the recent changes this process saw. Set `AuthorityTtl` well under your Sentinels' `down-after-milliseconds`, so that a process left connected to an old primary stops before another node is promoted.

**What this does not promise.** Redis copies writes to replicas after it replies. A failover can lose writes confirmed after Runwick's last check, which is at most a recheck interval plus the lease. The check proves the new primary has everything Runwick saw at its last check, not that nothing was lost. Runwick stops itself; it cannot stop other programs that write to a cut-off former primary. Receipts carry `redis.aof-always-sentinel-v1`.

**What it costs.** Expect a Sentinel setup to be somewhat slower than a lone primary, mostly because Redis copies every write to its replicas. In our drain tests, with every node on one shared machine, a Sentinel setup with two replicas was 12 to 34% slower than a lone primary (median 20%, six paired runs), and two replicas alone cost about 7% in an earlier test. Runwick sends the same commands per job either way, and its own Sentinel checks added no cost we could separate from noise. We have not measured nodes on separate machines.

## Cluster: many nodes, one owner per application (opt-in)

Every key of one application sits in one hash slot, so one cluster node (the slot's owner) holds the whole application and every script runs on that node. Different applications usually land on different nodes, so a cluster spreads applications, not the work of one application. Set `cluster-require-full-coverage no` on the nodes if you want one failing node to stop only its own applications: with the default `yes`, the whole cluster stops answering from the moment a node is seen as failed until its replica takes over. The Cluster option keeps the same rule as Sentinel: **Runwick only writes to the node it has just checked as the slot's owner, and stops writing the moment it cannot tell.**

```csharp
builder.UseRedis(
    "node1:6379,node2:6379,node3:6379,password=data-password",
    o => o.Cluster = new RedisClusterOptions());
```

List the cluster's nodes, every primary at least (replicas may be listed too), and no `serviceName`. Every primary must run the same settings as above, `appendfsync always` included; `everysec` cannot be combined with Cluster, and neither can Sentinel. Run `RunwickRedisMigrations.MigrateClusterAsync` (or `MigrateAsync` with `new RedisOptions { Cluster = new RedisClusterOptions() }`, or `runwick migrate --provider redis --redis-topology cluster`) with the same node list before you start the application: it checks every primary, and refuses one that holds Runwick keys but no store record. The `store` commands (status, admission, capability activation, re-identification) and `doctor` take the same option and look at every primary; if a primary that owns slots cannot be reached they refuse with `store_unavailable` instead of reporting part of the store.

`AuthorityRecheckInterval` and `AuthorityTtl` work as for Sentinel. Set `AuthorityTtl` well under the cluster's `cluster-node-timeout`, so that a process cut off from the cluster stops before a replica can be promoted.

**What Runwick checks each time.** Each listed node is asked who owns the application's slot. A majority of your listed nodes must name the same primary, and nobody may report that slot as moving or that owner as failing. The owner must pass the settings check. If it is a different node from the last one, it must continue the history: either the slot was moved by migration while the old owner stayed healthy (then the store's identity and revisions must be intact), or a replica was promoted after a failure (then it must have everything Runwick saw at its last check).

| Situation | What Runwick does |
|---|---|
| Most listed nodes are unreachable or disagree | Keeps writing until the lease runs out, then stops sending anything. Starts again as soon as a check passes. |
| The slot starts moving, the owner is reported failing, or a call is redirected (`MOVED`) | Stops sending anything at once and checks again. |
| The slot finished moving to another healthy node, or a failover promoted a replica that has everything | Moves to the new owner and resumes. Jobs and receipts written before are intact. |
| A promoted replica is behind what Runwick last saw, or the store identity or revision went backwards | **Blocked.** Every call fails as incompatible until you reconcile the histories and restart the process. |

Calls that are stopped are never sent. A call that was in flight when the slot moved can fail partway; it ends as "outcome unknown", and the half-finished change is completed on the new owner (the same recovery as after a crash). The Store page shows the state, the slot, its owner, the nodes the cluster reports and how many listed nodes agree.

**What this does not promise.** Everything said under Sentinel applies: Redis copies writes to replicas after it replies, a failover can lose writes confirmed after Runwick's last check, and Runwick cannot stop other programs from writing to a cut-off former owner. In addition: the store record (`rw:store`) lives on one slot's owner, which must be reachable when a process starts; one application is never spread over several nodes. Receipts carry `redis.aof-always-cluster-v1`.

**What it costs.** Because every key of one application sits on one node, Runwick's Cluster path sends about the same commands as standalone; finishes are split per slot, so a worker makes somewhat more round trips. In our one-host drain tests a one-node Cluster was within noise of standalone (six paired runs, from 24% slower to 14% faster). Replicas behind each primary cost what they cost under Sentinel.

## What Runwick checks

At startup, on every reconnect and every `ProfileRecheckInterval`, Runwick checks on a separate connection:

- the five settings above, through `CONFIG GET`;
- through `INFO`: `role:master`, `redis_mode:standalone`, `cluster_enabled:0`, AOF enabled, the last AOF write succeeded, and the version is at least 8.2;
- through `MODULE LIST`: the loaded modules, which are reported but allowed.

| When | A failed check means |
|---|---|
| At startup | The app does not start. The error names the setting and the value it saw, for example `appendfsync=everysec`. |
| While running | Runwick stops sending new work: no new claims, dispatches or schedule runs. Health reports the store as unhealthy (`store_profile_mismatch`) until a later check passes. Calls already sent finish as usual. |

Runwick sends its worker commands (claim, finish, renew) as ordinary Lua scripts (`EVALSHA`). The `UseFunctions` option (off by default) loads them instead as a Redis function library and calls them with `FCALL`. It is off by default because on drains it measured slower, not faster: 0.83 times as many jobs per second on disk and 0.89 times in memory. It gives the same results either way. It is for experiments, and for low-rate traffic where most calls carry a single job, since each call then skips redefining the script's helper functions. With it off, Runwick sends no `FUNCTION` or `FCALL` command, and the store description's `functions` value is `off`.

With `UseFunctions` on, the startup check loads the library with `FUNCTION LOAD`. The library's name, `rw_` and 16 hex digits, comes from its contents, so an older and a newer Runwick version can share one server, each with its own library. Redis keeps the library in the AOF and copies it to replicas. If it goes missing (for example after `FUNCTION FLUSH`), Runwick loads it again on the next call. This is not part of the check's verdict, and there is nothing to migrate: `runwick migrate --provider redis` does not touch it. If an ACL, a renamed command or a managed service blocks `FUNCTION` or `FCALL`, Runwick runs the same commands with `EVALSHA`, and the store description's `functions` value says so. To use the library, allow `FUNCTION LIST`, `FUNCTION LOAD` and `FCALL` for Runwick's user (for example `+function|list +function|load +fcall`). After an upgrade the older version's library stays on the server; once no running process uses that version, you can remove it with `FUNCTION DELETE <name>` (`FUNCTION LIST` shows the names).

Replicas attached to the primary are allowed and reported. But a replica promoted to primary is a different history, and without the Sentinel option Runwick does not follow a failover.

### History checks

Each process remembers the store's identity and the highest revision it has seen for the application. If Redis comes back empty (for example after `FLUSHALL`), with another store's identity, or with a lower revision, Runwick stops admitting work and treats every lease it held as lost. It does not resume until you restart the process against an intact store. This check catches a history that went backwards. It cannot prove that no write was lost.

## One application, one hash slot

Every key of an application starts with `rw:{<application>}:`, so all of them live in one hash slot. That is what lets one Lua script change a job's records together. Several applications can share one Redis database.

The cost: one application's throughput is bounded by one Redis server thread, and one very large command (for example a big batch) delays every other command of that application while it runs. If one application needs more, split the work into separate applications.

## No transactions with your data

Redis cannot join your business database's transaction. There is no `StageAsync` and no transactional completion on Redis. To create a job only when your business data commits, write it to an [outbox](/docs/outbox) in your business database; the relay delivers it to the Redis store.

## Wake-ups and polling

When a job that is due now becomes whole in the store, the write also publishes the queue's name on a Redis channel (`rw:{...}:wake`). Workers subscribe to it, so an idle worker usually starts a new job within milliseconds instead of waiting for its next poll. This is a hint only: a worker that loses its subscription goes back to polling every two seconds at most, and Redis does not keep a message nobody was listening for, so polling stays the way correctness is guaranteed.

For jobs that are delayed or waiting to retry, no message is sent when they fall due. Instead, each readiness check tells the worker when the next such job is due, and an idle worker sleeps until then (never less than 50 ms) rather than on its usual back-off. A delayed or retrying job that becomes the earliest waiting job of its queue and priority does publish the queue's name when it is written, so a worker that has been idle for a while learns about it at once instead of after its back-off (up to 12 seconds). Later delayed jobs behind it publish nothing.

## What Redis does not promise

- No high availability by default. With the Sentinel or Cluster option, a failover is followed and checked, but a promoted replica may have lost jobs confirmed after Runwick's last check. A cluster spreads applications over its nodes; it does not spread one application.
- Durability is the primary's disk and `appendfsync always`. Restoring an AOF or RDB file is a break in history.
- Running Redis without `appendfsync always` is supported only through the `everysec` option above, which Runwick checks and records on every receipt. Any other setting is refused.
- Results on Redis say nothing about speed compared with PostgreSQL.
